# المبادئ المعمارية الإلزامية لمشاريع ‎C#/.NET

هذه المبادئ إلزامية ولا يجوز الانحراف عنها. أي كود يُنتج يجب أن يلتزم بجميع المبادئ المطبقة أدناه. الانتهاك يُعدّ فشلًا في المهمة.

These principles are **MUST-Follow**. Every piece of code produced MUST comply with all applicable principles below. Violation constitutes task failure.

> **النطاق:** هذه المبادئ لمشاريع **‎C#/.NET** ولا تُطبَّق على مكدّسات أخرى. جوهر كل مبدأ ينطبق على كل مشروع ‎C#/.NET، والحلول الجديدة تعتمد MediatR وErrorOr (وقرار الحزم وتراخيصها في `/clean-architecture-structure`، قسم «Package Baseline and Licenses»). أمّا القواعد الخاصة بمكتبة بعينها فلا تنطبق إلا حين يكون للمشروع مرجعٌ إلى تلك المكتبة، وتُفحص كل مكتبة على حدة: قواعد MediatR (`ISender`، `IRequest`، `IPipelineBehavior`، `INotification` في المبادئ ٥ و٦ و٩ و١٠) تنطبق حين يُشار إلى MediatR؛ وقواعد ErrorOr (إرجاع `ErrorOr<T>`، ومصانع `Error`، و`IErrorOr` في المبادئ ٥ و٦ و٧) تنطبق حين يُشار إلى ErrorOr؛ وقواعد FluentValidation (المبدأ ١٠) تنطبق حين يُشار إلى FluentValidation. ومن دون المكتبة يبقى الجوهر قائمًا: المبدأ ٥ يُبقي معالِجات الأوامر منفصلة عن معالِجات الاستعلامات، والمبدأ ٦ يُبقي تنسيق حالة الاستخدام في معالِج واحد تستدعيه نقطة النهاية، وقواعدَ العمل في نموذج النطاق، والاهتمامات المشتركة في مُزخرِفات (decorators) حول المعالِجات لا في نقاط النهاية، والمبدأ ٧ يُبقي إخفاقات قواعد العمل نتائجَ مُرجَعة لا استثناءات، والمبدأ ٩ يُبقي أحداث النطاق داخل العملية.

| # | Principle | Enforcement Rule | Skill Reference |
|---|-----------|-----------------|-----------------|
| 1 | **Clean Architecture** | Dependencies flow inward. Each Domain project references no other project except a SharedKernel adopted by a repository ADR (bound by the same allowlist), and no package except the Domain allowlist: ErrorOr (P7) — or, in a project that does not reference ErrorOr, the one result-type library its Domain already uses, named in the repository ADR — plus `MediatR.Contracts` only when the repository has recorded Placement option A with the contracts variant (`/domain-driven-design` §4). No infrastructure in Domain or Application. An architecture test enforces the allowlist. | `/clean-architecture-structure` |
| 2 | **Domain-Driven Design (DDD)** | Aggregates, Entities, Value Objects, Domain Events, Bounded Contexts. Rich domain models with encapsulated behavior. Anemic models are prohibited. | `/domain-driven-design` |
| 3 | **SOLID Principles** | Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation, Dependency Inversion. Every class, every interface. | `/backend-development` |
| 4 | **OOP Fundamentals** | All four pillars enforced: **Encapsulation** (private fields, controlled access, no public setters on domain entities, state changes through behavior methods), **Abstraction** (hide complexity behind interfaces, program to abstractions not implementations), **Inheritance** (use judiciously, prefer composition; use a base class only for a real is-a relationship), **Polymorphism** (interfaces and virtual methods for varying behavior, no if/switch on type — use polymorphic dispatch; "type" means a CLR type or a discriminator value that selects behavior — a type code that stands in for a variant of a domain concept. Checking a framework-supplied state or status value inside infrastructure plumbing (change-tracker state, a retry record’s status, an upstream HTTP status class in an anti-corruption table) is not type dispatch either. Mapping a closed error-category enum such as `ErrorType` to the HTTP response (its status and the body members that the error contract defines for that type) inside the single HTTP error mapper (P7), and normalizing framework-produced problem types inside the single problem-details customization, are data mapping, not behavior dispatch; classifying exceptions by type inside the single global exception handler and the outage classifier it calls, and guard clauses that check an entity's state or invariants to allow or reject an operation, are not type dispatch either). No static mutable state. | |
| 5 | **CQRS** | Commands mutate state and return `ErrorOr<T>`. Queries read state and return `ErrorOr<T>`. Query handlers never change persisted state; filling a cache (cache-aside, `/backend-development` → Caching) is not a state change. Command handlers may read the state they need to validate and perform their write: their own context's state through write-side repositories, and another module's state through that module's public queries (`/clean-architecture-structure` → Module Boundaries). What is prohibited is one handler that both serves a read use case and changes state. Separate Command and Query objects via MediatR `IRequest<ErrorOr<T>>`. | `/clean-architecture-structure` |
| 6 | **MediatR Pipeline** | Endpoints send Commands/Queries via `ISender`. Use-case orchestration lives in handlers, never in endpoints; business rules live in the domain model (P2, P10). Cross-cutting concerns of use-case handling (validation, logging) use `IPipelineBehavior<,>`. HTTP-level concerns (authentication, endpoint authorization policies, rate limiting, request-shape filters, exception handling and error mapping) are configured once in the ASP.NET Core pipeline (`/backend-development` → Authorization, Error Pipeline). Request validation failures are expected outcomes: the validation behavior returns them as ErrorOr `Validation` errors (`TResponse` constrained to `IErrorOr`) and never throws. In-process side effects use `INotification` + `INotificationHandler`; a consumer that a messaging framework invokes for a broker message is their equivalent (`/event-driven-architecture` §7). No direct service calls from endpoints. | |
| 7 | **ErrorOr Pattern** | Command and query handlers return `ErrorOr<T>`; notification handlers and message consumers return `Task` and follow `/event-driven-architecture` §4 and §7. Domain errors are members of a static `{Concept}Errors` class in Domain: `static readonly` fields for errors with neither parameters nor metadata, and static methods, which build a new instance on every call, for errors that take parameters or carry metadata. They are never static fields that can be reassigned. No throwing exceptions for business rule violations. Exceptions are reserved for infrastructure faults and programming errors. ErrorOr errors reach HTTP through exactly one mapper in the API layer, which writes the single error contract owned by `/backend-development` (Response Format); the framework's own error responses use the same contract. | `/domain-driven-design` (§5 Domain Errors), `/backend-development` (Response Format) |
| 8 | **Strategy Pattern** | When exactly one of several implementations must be chosen at runtime, define an interface; each implementation declares the key it serves, and choosing is a lookup over the registered implementations: either a factory over `IEnumerable<IStrategy>` indexed by the declared key, or .NET keyed services (.NET 8+). Register strategies in DI. No `if/switch` over strategy keys or CLR types to choose an implementation, anywhere, including inside the factory. Mechanisms that run every implementation (notification handlers, pipeline behaviors) are not strategies. | |
| 9 | **Event-Driven Architecture** | Domain events for side effects inside the bounded context that raised them, in-process via MediatR. Integration events for reactions in other bounded contexts: other modules of a modular monolith, or other services. Synchronous calls between modules go only through the owning module's published contracts (`/clean-architecture-structure` → Module Boundaries). Typed contracts, ordering guarantees, idempotent consumers. No re-processing unless on failure. This does not restrict a use case's own calls to external services through typed clients (`/backend-development` → Outbound HTTP). | `/event-driven-architecture` |
| 10 | **DRY (Don't Repeat Yourself)** | When the same knowledge appears in 2+ places within one bounded context, extract it immediately to the owner that fits its kind. Cross-cutting use-case concerns go into an `IPipelineBehavior` (P6); HTTP-level concerns into the one ASP.NET Core pipeline. Domain rules go into the entity, value object or domain service that owns them. Technical helpers go into composed services or extension methods. Use a base class only for a real is-a relationship (P4). Code that looks similar but changes for different reasons is not duplication (P3). Do not extract domain models or business rules across bounded contexts; contexts exchange only IDs and published contracts. Framework-free base types (entity and value-object bases) live in one place: the SharedKernel project when the solution has one (a modular monolith always does), otherwise `Domain/Primitives/` (`/clean-architecture-structure` → Solution Layouts). Constants live in the innermost layer that owns their meaning: domain constants in `Domain/Constants/`, technical constants in the layer that uses them. Shared validators as reusable `FluentValidation` rules. | |

**Enforcement Rule:** Before completing any implementation, verify compliance with all applicable principles (see the scope note) using `/final-review-checklist` (Section 10). Any principle violation blocks completion.
