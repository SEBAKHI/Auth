## 1. بنية النظام

### البنية الطبقية

يتبع AuthSystem بنية طبقية صارمة حيث تتدفق التبعيات في اتجاه واحد فقط — الطبقات الخارجية تعتمد على الطبقات الداخلية، ولا يحدث العكس أبداً.

### مسؤوليات الطبقات

| القواعد | المسؤولية | الطبقة |
|---------|----------|--------|
| تستدعي API فقط؛ بدون منطق أعمال | عرض واجهة المستخدم والتفاعل | **العرض — Presentation** |
| تستدعي Services فقط؛ بدون وصول لقاعدة البيانات | توجيه الطلبات والتحقق من المدخلات وتنسيق الاستجابات | **واجهة API** |
| تستدعي Repositories فقط؛ تحتوي جميع قواعد الأعمال | منطق الأعمال والتنسيق وإدارة المعاملات | **الخدمات — Services** |
| تستدعي قاعدة البيانات فقط؛ بدون منطق أعمال | الوصول لقاعدة البيانات وتنفيذ الاستعلامات | **المستودعات — Repositories** |
| يُصل إليها فقط عبر Repositories | تخزين واسترجاع البيانات | **قاعدة البيانات** |

### قاعدة التبعيات

</div>

```
Database <- Repositories <- Services <- API <- Presentation
                     (التبعيات تتدفق للداخل فقط)
```

<div dir="rtl" lang="ar">

كل طبقة تتواصل فقط مع الطبقة التي فوقها مباشرة. طبقة العرض لا يمكنها الوصول لقاعدة البيانات مباشرة.

**لماذا هذا مهم:** إذا احتجت لتغيير قاعدة البيانات (مثلاً من SQL Server إلى PostgreSQL)، فإنك تغير طبقة Repository فقط. لا شيء آخر في النظام يحتاج لمعرفة ذلك.

## 2. تنفيذ الأمان

### تجزئة كلمات المرور: Argon2id

يستخدم AuthSystem خوارزمية **Argon2id حصرياً** — الخوارزمية الموصى بها من OWASP (2024) والفائزة بمسابقة تجزئة كلمات المرور الدولية (2015).

#### لماذا Argon2id على البدائل الأخرى؟

| القيد الرئيسي | الحالة | الخوارزمية |
|---------------|--------|------------|
| قابلة للكسر في ثوانٍ | **لا تُستخدم أبداً** | MD5 |
| سريعة جداً — لا مقاومة للقوة الغاشمة | **ليست لكلمات المرور** | SHA-256 |
| معالج فقط — لا تقاوم هجمات GPU بنفس الفعالية | **آمنة لكن تم تجاوزها** | bcrypt |
| تفتقر لصلابة الذاكرة؛ أضعف ضد الأجهزة الحديثة | **آمنة لكن تم تجاوزها** | PBKDF2 |
| لا هجمات عملية معروفة عند الإعداد الصحيح | **المعيار الذهبي الحالي** | **Argon2id** |

> تجمع Argon2id بين أفضل خصائص Argon2i (مقاومة هجمات القنوات الجانبية) و Argon2d (مقاومة كسر GPU). تتطلب ذاكرة كبيرة لكل محاولة، مما يجعل هجمات تخمين كلمات المرور الجماعية غير مجدية اقتصادياً.

#### الإعدادات (موصى بها من OWASP 2024)

| الغرض | القيمة | المعلمة |
|-------|--------|---------|
| تجعل كل محاولة مكلفة من حيث الذاكرة | 19 ميجابايت (19,456 كيلوبايت) | الذاكرة |
| عدد مرات المرور عبر الذاكرة | 2 | التكرارات |
| الخيوط لكل عملية تجزئة | 1 | التوازي |
| فريد لكل كلمة مرور — يمنع هجمات جداول قوس قزح | 16 بايت (عشوائي تشفيرياً) | الملح |
| حجم التجزئة الناتجة | 32 بايت | طول التجزئة |

**التنسيق المخزن:** `$argon2id$v=19$m=19456,t=2,p=1$[salt]$[hash]`

**إعادة التجزئة:** يكتشف النظام تلقائياً عندما تحتاج التجزئات المخزنة لإعادة التجزئة بسبب تغييرات الإعدادات ويرقّيها عند تسجيل الدخول الناجح التالي.

#### تفاصيل التنفيذ

- **المكتبة:** Konscious.Security.Cryptography.Argon2 الإصدار 1.3.1
- **مقارنة ثابتة الوقت:** تستخدم مقارنة ثابتة الوقت لمنع هجمات التوقيت
- **سجل كلمات المرور:** آخر 3 كلمات مرور مخزنة (مجزأة) لمنع إعادة الاستخدام

#### تحصين اختياري: الفلفل (Pepper) وفحص كلمات المرور المخترقة

طبقتان اختياريتان تكمّلان Argon2id (كلتاهما معطّلتان افتراضياً، وتُضبطان تحت `Password`):

- **الفلفل** (`Password:Pepper`) — سر من جانب الخادم (Argon2id `KnownSecret`) يُمزج في كل تجزئة ويُحفظ في مخزن الأسرار وليس في قاعدة البيانات. يدافع ضد اختراق قاعدة البيانات وحدها: بدون الفلفل تقاوم التجزئات المسروقة الكسر. تُرقّى التجزئات غير المُفلفَلة تلقائياً عند أول تسجيل دخول؛ وتُنسخ مادة المفتاح احتياطياً مثل مفاتيح JWT/HMAC.
- **فحص كلمات المرور المخترقة** (`Password:BreachedPasswordCheck`) — يفحص كلمات المرور الجديدة مقابل واجهة HIBP Pwned Passwords بخاصية k-anonymity (لا يغادر الخادم سوى بادئة تجزئة SHA-1). `Enforce` يرفض كلمات المرور المخترقة؛ و`Warn` يسمح بها لكن يعيد ترويسة `X-Password-Warning`. ويتحكم `FailOpen` بالسلوك عند تعذّر الوصول إلى HIBP.

### مصادقة الرموز: JWT RS256

يستخدم AuthSystem توقيع JWT غير متماثل (RS256) للمصادقة المبنية على الرموز.

| المدة | المحتويات | نوع الرمز |
|-------|----------|----------|
| 15 دقيقة | معرف المستخدم، الأدوار، الصلاحيات | **رمز الوصول — Access Token** |
| 7 أيام | معرف الجلسة | **رمز التحديث — Refresh Token** |

**لماذا RS256 (غير متماثل) بدلاً من HS256 (متماثل)؟**

</div>

```
متماثل (HS256):
  نفس المفتاح للتوقيع والتحقق = يجب مشاركة السر مع جميع المتحققين

غير متماثل (RS256):
  المفتاح الخاص: يوقع الرموز (يبقى سرياً على خادم المصادقة)
  المفتاح العام: يتحقق من الرموز (يوزع بأمان لأي خدمة)
  النتيجة: الخدمات الأخرى تتحقق من الرموز دون معرفة سر التوقيع
```

<div dir="rtl" lang="ar">

**دورة حياة الرمز:**
1. المستخدم يصادق ← يحصل على رمز وصول + رمز تحديث
2. رمز الوصول يُستخدم لطلبات API (نافذة 15 دقيقة)
3. عند انتهاء رمز الوصول ← رمز التحديث يُستخدم للحصول على زوج جديد
4. عند تسجيل الخروج أو حدث أمني ← الرموز تُضاف للقائمة السوداء
5. القائمة السوداء تُفحص مع كل طلب قبل منح الوصول

### إدارة المفاتيح

- **أوضاع التخزين** (`SecretManagement:StorageMode`): **PlainText** (المفاتيح في `appsettings.Production.json`، عبر المنصات)، أو **Certificate** (المفاتيح مشفّرة في `secrets.dpapi` ومحمية بشهادة X.509 تملكها — محمولة بين الخوادم)، أو **Dpapi** (تشفير Windows المرتبط بالجهاز). يُوصى بوضع Certificate للاستضافة المشتركة؛ وPlainText هو الافتراضي والخيار الوحيد عبر المنصات (Linux/cPanel).
- **موقع حلقة المفاتيح:** `DataProtection:KeyPath` (الافتراضي `%ProgramData%/AuthSystem/Keys`؛ وجّه Auth API والبوابة إلى نفس المجلد ليتشاركا حلقة واحدة)
- **التوليد التلقائي:** تتولد مفاتيح RSA وHMAC ورمز البوابة عند أول تشغيل؛ اضبط `AutoGenerateKeys: false` بعدها كي تفشل الأسرار المفقودة بصوت عالٍ بدلاً من إعادة التوليد بصمت
- **مفاتيحك الخاصة (BYOK):** استورد مادة RSA/HMAC/رمز البوابة عبر واجهة إدارة الأسرار (Certificate/Dpapi) أو `appsettings.Production.json` (PlainText) — يتيح ترحيل الخادم دون تسجيل خروج أحد
- **التدوير:** تدوير المفاتيح مدعوم بدون إبطال الرموز الحالية (مفاتيح نشطة متعددة)

### تحديد معدل الطلبات

| الغرض | النافذة الزمنية | الحد | نقطة النهاية |
|-------|----------------|------|--------------|
| يضمن نجاح محاولات الدخول الشرعية فقط | 60 ثانية | 5 طلبات | **تسجيل الدخول** |
| حماية عمليات المصادقة | 60 ثانية | 20 طلباً | **نقاط نهاية المصادقة** |
| الحفاظ على توفر الخدمة | 60 ثانية | 100 طلب | **API العام** |
| إدارة الحركة على مستوى النظام | 60 ثانية | 1,000 طلب | **البوابة (شامل)** |

عند تجاوز الحد، يستجيب الخادم برمز HTTP 429 (طلبات كثيرة جداً) مع رأس `Retry-After` يشير إلى متى يمكن للعميل إعادة المحاولة.

### رؤوس الأمان (امتثال OWASP)

كل استجابة تتضمن رؤوس حماية:

| الحماية ضد | القيمة | الرأس |
|------------|--------|-------|
| هجمات اختطاف النقرات | DENY | X-Frame-Options |
| استنشاق نوع MIME | nosniff | X-Content-Type-Options |
| البرمجة عبر المواقع (XSS) | 1; mode=block | X-XSS-Protection |
| حقن البرامج النصية | default-src 'self' | Content-Security-Policy |
| تخفيض البروتوكول إلى HTTP | max-age=31536000 | Strict-Transport-Security |

### حماية الحساب

| القيمة | الحماية |
|--------|---------|
| 5 محاولات | محاولات الدخول الفاشلة قبل القفل |

| 8 أحرف (يُوصى بـ 12+) | الحد الأدنى لطول كلمة المرور |

### الثغرات المُخَففة

| كيف يمنعها AuthSystem | الثغرة |
|----------------------|--------|
| استعلامات ذات معلمات عبر Dapper — مدخلات المستخدم لا تُعامل أبداً ككود SQL | **حقن SQL** |

## 3. بنية الأداء

يحقق AuthSystem أداءً عالياً من خلال أربعة قرارات تصميم رئيسية:

### 1. مكتبة Dapper: تنفيذ SQL مباشر

بدلاً من استخدام ORM ثقيل يولد SQL تلقائياً، يستخدم AuthSystem مكتبة **Dapper** — وهي Micro-ORM تنفذ استعلامات SQL مكتوبة يدوياً ومحسنة.

| Dapper (مكتبة Micro-ORM) | ORM كامل (مثل Entity Framework) | الجانب |
|---------------------------|----------------------------------|--------|
| SQL مكتوب يدوياً ومحسّن | SQL يُولد تلقائياً، قد يكون غير فعال | تنفيذ الاستعلامات |
| الحد الأدنى (بدون تتبع) | أعلى (تتبع الكائنات، اكتشاف التغييرات) | عبء الذاكرة |
| تحكم كامل | مجرد عن المطور | التحكم في SQL |
| مباشر وشفاف | تجريد عالي المستوى | التعقيد |

> مقاييس الأداء تختلف حسب البيئة وتعقيد الاستعلام. ميزة Dapper أكثر وضوحاً في أحمال العمل كثيفة القراءة على جداول مفهرسة.

### 2. نمط Async/Await: عمليات غير محجوبة

كل استدعاء لقاعدة البيانات غير متزامن مع دعم **CancellationToken**. الخادم لا ينتظر انتهاء عملية قبل بدء أخرى — طلبات متعددة تُعالج بالتزامن.

### 3. تجميع الاتصالات — Connection Pooling

اتصالات قاعدة البيانات يُعاد استخدامها من مجمع بدلاً من إنشائها من جديد لكل طلب. هذا يلغي عبء إنشاء اتصالات جديدة (عادة 50 مللي ثانية لكل منها)، مما ينتج عنه زمن انتظار شبه صفري.

### 4. التخزين المؤقت في الذاكرة

البيانات المستخدمة بشكل متكرر تُخزن مؤقتاً في الذاكرة:

| استراتيجية التخزين المؤقت | البيانات |
|---------------------------|----------|
| في الذاكرة (يُفحص مع كل طلب) | قائمة الرموز الملغاة — Token Blacklist |
| تذكر لكل طلب | عمليات البحث عن الصلاحيات |
| تحميل عند البدء | الإعدادات |

## 4. تصميم API والأنماط

### تصميم RESTful

يتبع AuthSystem مبادئ REST:

| التطبيق | المبدأ |
|---------|--------|
| `/users` و `/roles` (ليس `/getUsers`) | **الموارد كأسماء** |
| GET (قراءة) و POST (إنشاء) و PUT (تحديث) و DELETE (حذف) | **أفعال HTTP للإجراءات** |
| كل طلب يحمل جميع المعلومات المطلوبة (رمز JWT) | **بدون حالة** |
| `/api/v1/{resource}/{id}/{sub-resource}` | **عناوين URL متسقة** |

### مسؤولية واحدة لكل نقطة نهاية

</div>

```
GET  /api/v1/users         -> قائمة المستخدمين
GET  /api/v1/users/{id}    -> الحصول على مستخدم واحد
POST /api/v1/users         -> إنشاء مستخدم
PUT  /api/v1/users/{id}    -> تحديث مستخدم
```

**فقط طبقة Repositories يمكنها الوصول لقاعدة البيانات.**

</div>

صحيح:
Controller -> Service -> Repository -> Database

خطأ:
Controller -> Database (تجاوز الطبقات)

## 5. مبادئ التصميم

### مبدأ DRY — لا تكرر نفسك

المنطق المشترك مركزي في خدمات قابلة لإعادة الاستخدام. مثال: منطق تجزئة كلمات المرور موجود في مكان واحد (`Argon2PasswordHasher`)، يُستخدم من كل من تسجيل الدخول والتسجيل. إصلاح خطأ في مكان واحد يصلحه في كل مكان.

### مبادئ SOLID

| التطبيق في AuthSystem | المبدأ |
|----------------------|--------|
| كل خدمة/متحكم/مستودع له وظيفة واحدة | **مسؤولية واحدة — S** |
| يمكن إضافة أنواع صلاحيات أو طرق مصادقة جديدة دون تعديل الكود الحالي | **مفتوح/مغلق — O** |
| واجهات المستودعات قابلة للتبادل (مثلاً استبدال SQL Server بـ PostgreSQL) | **استبدال ليسكوف — L** |
| واجهات منفصلة للقراءة/الكتابة — المستهلكون يعتمدون فقط على ما يستخدمونه | **فصل الواجهات — I** |
| جميع الخدمات تعتمد على واجهات (تجريدات)، وليس تنفيذات محددة؛ تُربط عبر حقن التبعيات | **عكس التبعية — D** |

## 8. التعافي من الكوارث واستمرارية الأعمال

### استراتيجية النسخ الاحتياطي

| الاحتفاظ | التكرار | طريقة النسخ | المكون |
|----------|---------|------------|--------|
| 30 يوماً | كامل: يومياً؛ تفاضلي: كل 6 ساعات | نسخ احتياطي كامل + تفاضلي لـ SQL Server | **قاعدة البيانات** |
| غير محدود | عند كل تغيير | التحكم بالمصدر (appsettings، عمليات الترحيل) | **الإعدادات** |
| حتى انتهاء جميع الرموز الموقعة بالمفتاح القديم | عند التدوير | `secrets.dpapi` + حلقة المفاتيح (+ ملف `.pfx` في وضع Certificate)؛ أو `appsettings.Production.json` في PlainText | **الأسرار** (RSA/HMAC/رمز البوابة، الفلفل) |
| حسب متطلبات الامتثال (عادة 1-7 سنوات) | يومياً | نسخ قاعدة البيانات + تصدير CSV اختياري | **سجلات التدقيق** |

### أهداف الاسترداد (المستهدفات الموصى بها)

| الوصف | المستهدف | المقياس |
|-------|---------|---------|

| الحد الأقصى المقبول لوقت التوقف | ساعة واحدة | **RTO** — هدف وقت الاسترداد |

### الاستجابة للحوادث

1. **الاكتشاف**: تنبيهات آلية عند ارتفاع محاولات المصادقة الفاشلة أو تجاوز حدود المعدل أو فشل فحوصات الصحة
2. **الاحتواء**: قفل الحساب التلقائي، إضافة الرموز للقائمة السوداء، تصعيد تحديد المعدل
3. **التحقيق**: تتبع الطلبات عبر معرفات الارتباط من خلال السجلات المنظمة
4. **الاسترداد**: استعادة قاعدة البيانات، تدوير المفاتيح، إعادة تعيين كلمات المرور إجبارياً عند الحاجة
5. **ما بعد الحادث**: مراجعة سجل التدقيق، تحليل السبب الجذري، تحديث السياسات

## 10. إدارة الأسرار وتدوير المفاتيح

### حماية الأسرار الحالية

| طريقة الحماية | السر |
|-------------|------|
| `StorageMode`: PlainText (`appsettings.Production.json`)، أو Certificate (`secrets.dpapi` + شهادة X.509)، أو Dpapi (مرتبط بجهاز Windows) | مفاتيح توقيع RSA، مفتاح HMAC، رمز البوابة |
| متغير البيئة `ConnectionStrings__AuthDb`، أو مشفّرة في `secrets.dpapi` (Certificate/Dpapi) | سلسلة اتصال قاعدة البيانات |
| متغير البيئة `Email__Password`، أو مشفّرة في `secrets.dpapi` | كلمة مرور SMTP |
| تُخزَّن في مخزن الأسرار النشط (عند التفعيل) | فلفل كلمة المرور |
| مجزأة بـ Argon2id | مفاتيح API (المخزنة) |
| تُرسل عبر رأس `X-Gateway-Token` | رمز البوابة (أثناء النقل) |

### عملية تدوير المفاتيح

1. **توليد زوج مفاتيح جديد** — مفاتيح RSA جديدة تُنشأ
2. **فترة المفتاح المزدوج** — المفتاح القديم والجديد كلاهما نشطان للتحقق
3. **الانتقال** — الرموز الجديدة تُوقع بالمفتاح الجديد؛ الرموز القديمة لا تزال قابلة للتحقق
4. **التقاعد** — المفتاح القديم يُزال بعد انتهاء جميع الرموز الموقعة به (الحد الأقصى: مدة رمز التحديث = 7 أيام)

> **التزويد:** تتولد الأسرار عند أول تشغيل (`AutoGenerateKeys: true`)؛ اضبطها على `false` بعدها. وللتحكم بمادة المفاتيح بنفسك، استخدم نقاط نهاية `import/*` الإدارية (Certificate/Dpapi) أو حرّر `appsettings.Production.json` (PlainText) — راجع PRODUCTION_DEPLOYMENT_GUIDE.md §G.

لعمليات النشر الإنتاجية، التكامل مع:

- **HashiCorp Vault**
