# AuthSystem — التعمق التقني

## دليل البنية والتنفيذ والعمليات

كُتب هذا المستند لمهندس معماري أو مهندس أول لم يرَ هذه الشيفرة من قبل، ويريد أن يحكم بنفسه على متانة التصميم. وهو يصف النظام **كما هو اليوم**، لا كما قد يصير. وحيثما وُجد شيء مضبوط في الإعدادات لكنه لا يفعل شيئاً، ذُكر ذلك صراحةً بدل إغفاله؛ والقسم 19 يجمع هذه الحالات كلها في مكان واحد.

كل اختصار يُشرح عند أول ظهور له. وكل رقم في هذا المستند جاء بالعدّ من شجرة الشيفرة المصدرية، لا بالتقدير.

## 1. بنية النظام

### ما الذي يعمل فعلاً

**AuthSystem أربعة أشياء تعمل وقاعدة بيانات واحدة.** واجهة برمجة تطبيقات (API — Application Programming Interface) تعمل فوق بروتوكول نقل النص التشعبي (HTTP — HyperText Transfer Protocol) وتحمل السلوك كله؛ ووكيل عكسي يقف أمامها عند حافة الشبكة؛ وتطبيقان يعملان داخل المتصفح وهما الواجهتان الوحيدتان اللتان يلمسهما إنسان. وكل حالة دائمة تعيش في قاعدة بيانات SQL Server واحدة.

| ‏مكانها في المستودع | ‏ما هي | ‏الوحدة |
|---|---|---|
| ‏`Auth/Auth_API` | ‏تطبيق ويب على ASP.NET Core — كل عملية أعمال | ‏Auth API |
| ‏`Auth/API_Gateway` | ‏وكيل عكسي مبني على YARP (Yet Another Reverse Proxy) | ‏بوابة API |
| ‏`Auth_UI/apps/console` | ‏واجهة المسؤول، وهي تطبيق React أحادي الصفحة (SPA — Single-Page Application) | ‏تطبيق الكونسول |
| ‏`Auth_UI/apps/accounts` | ‏واجهة الخدمة الذاتية للمستخدم النهائي، وهي أيضاً تطبيق React أحادي الصفحة | ‏تطبيق الحسابات |
| ‏`Auth/Auth_DB` | ‏SQL Server، يُنشر من مشروع SQL Server Data Tools (SSDT) | ‏قاعدة البيانات |

لا يوجد أي مكوّن آخر من جانب الخادم. لا توجد صورة حاوية، ولا وسيط رسائل، ولا خادم تخزين مؤقت، ولا مخزن بيانات ثانٍ.

### الحل ومشاريعه

يعلن ملف الحل **أحد عشر مشروعاً: عشرة مشاريع C# ومشروع قاعدة بيانات SQL Server واحد.** وكل مشروع C# يستهدف `net10.0` (‏.NET 10). أما مشروع قاعدة البيانات فتبنيه سلسلة أدوات ‎.NET Framework منفصلة، وهو يستهدف مزوّد مخطط SQL Server 2019.

*في الشيفرة:* `Auth/Auth.sln`؛ وأطر الهدف داخل كل ملف `.csproj`؛ و`Auth/Auth_DB/Auth_DB.sqlproj`.

| ‏المشاريع التي يشير إليها | ‏الغرض منه | ‏المشروع |
|---|---|---|
| ‏**لا شيء** | ‏الكيانات والتجميعات وكائنات القيمة وأحداث النطاق وفهارس الأخطاء وواجهات المستودعات | ‏`Auth.Domain` |
| ‏`Auth.Domain` | ‏الأوامر والاستعلامات ومعالجاتها، وكائنات نقل البيانات (DTO — Data Transfer Object)، وفئات الإعدادات، والمدققات | ‏`Auth.Application` |
| ‏`Auth.Domain` و`Auth.Application` و`Auth.Shared` و`Auth_Localization` | ‏مستودعات Dapper والتشفير وإصدار الرموز وعرض الإشعارات ومزودات الإعدادات | ‏`Auth.Infrastructure` |
| ‏`Auth.Infrastructure` و`Auth_Localization` | ‏مضيف الويب — المتحكمات والوسائط البرمجية ومعالجات الأحداث وكل ربط حقن التبعيات | ‏`Auth_API` |
| ‏`Auth.Shared` و`Auth_Localization` | ‏الوكيل العكسي القائم على YARP | ‏`API_Gateway` |
| ‏**لا شيء** | ‏مساعدات بدء التشغيل والأسرار وحماية البيانات، إضافة إلى وسيط رؤوس الأمان الذي يتشاركه المضيفان | ‏`Auth.Shared` |
| ‏**لا شيء** | ‏موارد الترجمة المضمّنة لسبع لغات، ووسيط التوطين | ‏`Auth_Localization` |
| ‏**لا شيء** | ‏مكتبة عميل قابلة لإعادة التوزيع لتطبيقات ‎.NET من الأطراف الثالثة | ‏`Auth.Sdk` |
| ‏`Auth.Infrastructure` | ‏أداة سطر أوامر من 23 سطراً تطبع تجزئة كلمة مرور وجملة SQL اللازمة لتطبيقها | ‏`Auth_Setup` |
| ‏`Auth_API` و`Auth.Infrastructure` | ‏مشروع اختبارات الواجهة الخلفية الوحيد | ‏`Auth_API.Tests` |
| ‏— | ‏مشروع قاعدة البيانات بصيغة SSDT (المخطط والبذور وسكربتات الترقية) | ‏`Auth_DB` |

هناك حافتان في هذا الجدول جديرتان بالانتباه معمارياً، وتُذكران هنا بدل إخفائهما خلف رسم مثالي.

**‏`Auth_API` لا يشير إلى `Auth.Application` ولا إلى `Auth.Domain` إطلاقاً.** فهو يصل إليهما بشكل غير مباشر عبر `Auth.Infrastructure`، رغم أن شيفرته تستخدم مساحات أسمائهما في كل صفحة تقريباً. ونتيجة ذلك أن مضيف API لا يمكن ترجمته أمام الطبقات الداخلية دون الطبقة الخارجية، فقول «‏API يعتمد على التجريدات فقط» ليس مفروضاً بواسطة رسم المشاريع — إنه عُرف لا أكثر. والأمر نفسه ينطبق على `Auth.Shared`.
*في الشيفرة:* `Auth/Auth_API/Auth_API.csproj` السطران 26-27.

**‏`Auth.Infrastructure` يشير إلى `Auth_Localization`.** هذه هي الحافة الوحيدة التي تتجه من طبقة أدنى نحو مشروع موارد، وهي موجودة لأن عرض الإشعارات يحلّ النصوص المترجمة داخل طبقة البنية التحتية. إنها استثناء مقصود من قاعدة «التبعيات للداخل فقط»، لا خطأ عرضي.
*في الشيفرة:* `Auth/Auth.Infrastructure/Auth.Infrastructure.csproj` السطر 30.

**‏`Auth.Sdk` يتيم.** لا يشير إليه أي مشروع في الحل. هو مدرج في ملف الحل، ولا شيء آخر يُبنى أمامه. والقسم 14 يوضح ما يعنيه ذلك بالنسبة إلى عيوبه المعروفة.

### العمارة النظيفة كما تُمارَس فعلاً

التبعيات تتدفق إلى الداخل: `Auth.Domain` ← `Auth.Application` ← `Auth.Infrastructure` ← `Auth_API`. ولا شيء يشير إلى مضيف API سوى مشروع الاختبارات. وواجهات المستودعات مُعلنة في `Auth.Domain` (‏39 واجهة، واحدة لكل نوع كيان مُخزَّن) ومُنفَّذة في `Auth.Infrastructure` (‏41 فئة)، فلا يرى `Auth.Application` أنواع Dapper ولا أنواع SQL Server أبداً.

حقيقتان ينبغي للمهندس المعماري معرفتهما قبل قراءة الشيفرة:

- **لا توجد دوال تسجيل موسَّعة لكل طبقة.** لا وجود لـ `AddApplication()` ولا `AddInfrastructure()` ولا `AddPersistence()`. كل تسجيل خدمة في النظام يحدث مباشرةً داخل ملف واحد من التعليمات عالية المستوى، طوله 1,075 سطراً.
  *في الشيفرة:* `Auth/Auth_API/Program.cs`.
- **لا يوجد نمط وحدة العمل (Unit of Work).** لا وجود لنوع اسمه `IUnitOfWork`. المعالج لا يملك معاملة. بل المستودع هو الذي يفتح واحدة بنفسه عبر `connection.BeginTransaction()`، وذلك فقط حين تحتاج عملية واحدة إلى الكتابة في عدة جداول دفعةً واحدة — وسبعة ملفات تفعل ذلك.

### كيف يُعالَج الطلب

منطق الأعمال يعيش في **190 معالجاً من معالجات MediatR**، لا في خدمات. لا توجد في هذا المستودع فئة اسمها `AuthService` ولا `UserService` ولا `RoleService`.

المعالجات الـ190 هي 120 معالج أوامر و70 معالج استعلامات، منظّمة في **17 مجال ميزة** تحت المسار `Auth/Auth.Application/Features/<Area>/<UseCase>/`. وكل حالة استخدام مجلد مستقل يضم سجل الأمر أو الاستعلام، ومعالجه، ومدققاً في الغالب.

مسار التوجيه واحد لكل نقطة نهاية:

1. **المتحكم يستقبل طلب HTTP.** وهو يحقن `ISender` — واجهة الإرسال فقط في MediatR — بدل أي فئة خدمة. و23 متحكماً من أصل 25 متحكماً قابلاً للتوجيه تعمل بهذه الطريقة؛ والاستثناءان هما متحكم إعدادات البوابة الداخلي ومتحكم رفع الصور.
2. **المتحكم يرسل أمراً أو استعلاماً.** كل واحد منها `record` في C# يطبّق `IRequest<ErrorOr<T>>` — أي فصل مسؤولية الأوامر عن الاستعلامات (CQRS — Command Query Responsibility Segregation) مع تضمين نوع النتيجة في العقد نفسه.
3. **‏`LoggingBehavior` يعمل أولاً.** يسجل الدخول بمستوى Information، ويسجل تحذيراً حين تكون النتيجة خطأً، ويسجل تحذيراً ثانياً حين يستغرق المعالج أكثر من **500 مللي ثانية**.
   *في الشيفرة:* `Auth/Auth.Application/Behaviors/LoggingBehavior.cs` السطر 49.
4. **‏`ValidationBehavior` يعمل ثانياً.** ينفّذ كل مدقق FluentValidation مسجَّل لذلك الطلب على التوازي، ويقطع المسار بأخطاء تحقق إذا فشل أي منها.
   *في الشيفرة:* `Auth/Auth.Application/Behaviors/ValidationBehavior.cs` السطور 34-49.
5. **المعالج يعمل** ويعيد `ErrorOr<T>` — إما القيمة وإما قائمة أخطاء. ومخالفات قواعد الأعمال تُعاد كأخطاء، ولا تُرمى استثناءات أبداً.
6. **المتحكم يحوّل النتيجة إلى HTTP.** فئة أساس مشتركة واحدة تربط أنواع الأخطاء برموز الحالة وتبني جسم `ProblemDetails`. والقسم 18 يعطي الشكل الدقيق.
   *في الشيفرة:* `Auth/Auth_API/Common/ApiController.cs` السطور 32-57.

**هذان السلوكان هما الوحيدان المسجَّلان، وبهذا الترتيب.** لا يوجد سلوك معاملات، ولا سلوك تخزين مؤقت، ولا سلوك تفويض، ولا سلوك قياس أداء.
*في الشيفرة:* `Auth/Auth_API/Program.cs` السطران 670-671.

### أحداث النطاق

هناك **34 سجل حدث نطاق** و**38 معالج إشعارات** تستهلكها. وتتعايش آليتا توجيه، ومن المفيد معرفة ذلك قبل البحث عن واحدة منهما:

- **أحداث تطلقها التجميعة.** التجميعة تُلحق الحدث بقائمة خاصة، ثم يقوم موجّه بنسخها وتفريغها ونشرها. ولا يوجد في طبقة النطاق كلها سوى 11 موضع إطلاق، جميعها داخل `User` و`NotificationTemplate`.
- **أحداث تُنشر مباشرة.** 27 معالجاً يحقن `IPublisher` وينشر الحدث بنفسه. وهذا هو المسار الغالب.

تُسمّى المعالجات بالنمط `[EventName][Audit|Notification]EventHandler`، مثل `UserCreatedAuditEventHandler`.

وهناك حدثان **بلا أي معالج**: `WebhookKeyCreatedEvent` و`WebhookKeyRevokedEvent`. ولذلك فإن إنشاء مفتاح Webhook لا يكتب أي مدخلة تدقيق، بخلاف إنشاء مفتاح API. راجع القسم 19.

### ترتيب الوسائط البرمجية في HTTP

هذا هو الترتيب الدقيق داخل مضيف API بعد بناء التطبيق. وكل مرحلة إما تحوّل الطلب وإما ترفضه.

1. **‏`UseHsts`** — يرسل رأس أمان النقل الصارم (HSTS — HTTP Strict Transport Security). **يُتخطى في بيئة التطوير.**
2. **‏`UseForwardedHeaders`** — يقرأ `X-Forwarded-For` و`X-Forwarded-Proto`. ولا توجد قائمة وكلاء موثوقين مضبوطة، فتُقبل هذه الرؤوس من أي طرف يستطيع الوصول إلى API مباشرة.
3. **‏`SecurityHeadersMiddleware`** — يكتب رؤوس أمان الاستجابة المذكورة في القسم 3.
4. **‏`UseSerilogRequestLogging`** — سطر سجل منظَّم واحد لكل طلب.
5. **‏`UseAuthLocalization`** — يختار لغة الاستجابة.
6. **‏`ExceptionHandlingMiddleware`** — يحوّل الاستثناءات غير المعالَجة إلى `application/problem+json`.
7. **‏`GatewayTokenValidationMiddleware`** — يرفض بالرمز **403** أي طلب لم يصل عبر البوابة. والقسم 2 يشرح المصافحة واستثناءاتها.
8. **‏`MapOpenApi`** — يقدم مستند OpenAPI. **في بيئة التطوير فقط.**
9. **‏`UseHttpsRedirection`**.
10. **‏`UseStaticFiles`** — يقدم مخزن الصور المرفوعة.
11. **‏`UseCors`** — سياسة مشاركة الموارد عبر الأصول (CORS — Cross-Origin Resource Sharing)، تُعاد بناؤها من الإعدادات الحية مع كل طلب.
12. **‏`UseRateLimiter`**.
13. **‏`UseAuthentication`** — يتحقق من رمز الحامل.
14. **‏`JwtBlacklistValidationMiddleware`** — يرفض بالرمز **401** أي رمز أُلغي بعد إصداره. وهذا يعمل *بعد* المصادقة و*قبل* التفويض، عن قصد.
15. **‏`UseAuthorization`** — يقيّم سياسات الصلاحيات.
16. **‏`MapHealthChecks("/health")`** و**‏`MapHealthChecks("/ready")`**.
17. **‏`MapControllers`**.

*في الشيفرة:* `Auth/Auth_API/Program.cs` السطور 910-1020.

### تطبيقا المتصفح

يعيش التطبيقان في `Auth_UI/`، وهي مساحة عمل pnpm تضم **تطبيقين وخمس حزم مشتركة**. وهما تطبيقان بلغة React أحاديا الصفحة، أي أن المتصفح ينزّل حزمة JavaScript واحدة ثم يعرض كل شاشة محلياً ويطلب البيانات من API. ولا توجد في هذا المستودع واجهة إدارة تُعرض من الخادم.

| ‏تطبيق الحسابات | ‏تطبيق الكونسول | ‏ |
|---|---|---|
| ‏`@authsystem/accounts` | ‏`@authsystem/console` | ‏اسم مساحة العمل |
| ‏`Auth_UI/apps/accounts` | ‏`Auth_UI/apps/console` | ‏المجلد |
| ‏مستخدم نهائي يدير حسابه الخاص | ‏مسؤول يدير المنصة | ‏من يستخدمه |
| ‏`https://localhost:5174` | ‏`https://localhost:5173` | ‏عنوان التطوير |
| ‏واجهة Auth API نفسها | ‏واجهة Auth API، والقيمة الافتراضية `https://localhost:5101` | ‏يتحدث إلى |

خادما التطوير كلاهما **يعملان بـHTTPS حصراً** مع `strictPort: true`، وذلك عن قصد كي يحتفظ المتصفح بملف تعريف جلسة مزود الهوية. وتأتي شهادتاهما من متغيري البيئة `DEV_HTTPS_CERT` و`DEV_HTTPS_KEY`.

**وبدون هذين المتغيرين يبدأ الخادم رغم ذلك — فهو يحذّر ثم يرتدّ إلى HTTP العادي.** وذلك الارتداد هو بعينه العطل الذي وُجدت قاعدة HTTPS لتمنعه: فقاعدة Chrome في «الموقع نفسه مع المخطَّط» تجعل `http://localhost` و`https://localhost` موقعين مختلفين، فيرفض المتصفح في صمت تخزين ملف تعريف جلسة مزود الهوية الموسوم `SameSite=Lax` والمسكوك عبر `POST /auth/login`. فيبدو تسجيل الدخول ناجحاً، ويرتدّ `/auth/authorize` مباشرةً إلى `/login`، ولا يوجد خطأ في أي مكان تشير إليه. فاضبط المتغيرين كليهما قبل أول محاولة تسجيل دخول.
*في الشيفرة:* `Auth_UI/apps/console/vite.config.ts` السطر 15؛ و`Auth_UI/apps/accounts/vite.config.ts` السطر 14؛ و`Auth_UI/dev-https.ts`.

والحزم المشتركة الخمس هي:

| ‏ما تحتويه | ‏الحزمة |
|---|---|
| ‏عميل API المُنمَّط، ومخزن الرموز، ومزامنة الجلسة بين التبويبات، وربط الأخطاء | ‏`@authsystem/api` |
| ‏سياق الجلسة، وحُرّاس المسارات، وشاشات تسجيل الدخول المشتركة | ‏`@authsystem/auth` |
| ‏لغات العرض السبع واتجاه النص | ‏`@authsystem/i18n` |
| ‏مكتبة مكونات shadcn/ui وجدول البيانات المشترك | ‏`@authsystem/ui` |
| ‏شاشات الملف الشخصي والمؤسسات، ويركّبها **كلا** التطبيقين | ‏`@authsystem/account` |

**حزمة التقنيات:** React 19، وVite 8، وTypeScript 6، وTailwind CSS 4، وshadcn/ui على أساس Radix، وأيقونات lucide، وReact Router 7، وTanStack Query وTable، وreact-hook-form مع zod، وi18next، وsonner، وrecharts.

**كيف يصادقان المستخدم.** يسجّل كلا التطبيقين دخول المستخدم بإرسال بيانات الاعتماد إلى نقطة نهاية تسجيل الدخول في API، ثم يحتفظان بالرموز العائدة داخل المتصفح. ويُحفظ رمز الوصول **في الذاكرة فقط** ولا يُكتب على القرص أبداً؛ أما رمز التحديث فيُخزَّن في `localStorage` تحت المفتاح `auth.refreshToken` كي تستطيع إعادة تحميل الصفحة استئناف الجلسة بصمت. ولأن رمز التحديث يُستخدم مرة واحدة ويعامل الخادمُ تقديمه مرة ثانية على أنه سرقة، فإن كل تبويب من تبويبات الأصل ينسّق التجديد عبر قفل `BroadcastChannel` بدل أن يسابق بتحديث خاص به. وتسجيل الدخول نفسه يضبط أيضاً ملف تعريف جلسة مزود الهوية على الخادم، وهو ما يتيح لتطبيق *طرف ثالث* إتمام تدفق رمز التفويض الموصوف في القسم 4 دون مطالبة المستخدم بكلمة مروره من جديد.
*في الشيفرة:* `Auth_UI/packages/api/src/token-store.ts` و`tab-sync.ts` و`client.ts`.

**إلى أين يُبنيان.** يُبنى كل تطبيق إلى مجلد `dist/` خاص به باستخدام موقع الإخراج الافتراضي في Vite — فلا إعداد Vite في أي منهما يتجاوز هذا الموقع، ومجلد `dist` مستثنى من git. ويُنسخ ملف `public/web.config` الخاص بكل تطبيق إلى ذلك المجلد أثناء البناء، وهو ما يضبط خادم معلومات الإنترنت (IIS — Internet Information Services) لتقديم التطبيق أحادي الصفحة: إعادة كتابة كل مسار غير مطابق إلى `index.html`، وعدم تخزين `index.html` مؤقتاً أبداً، وتخزين `/assets` مؤقتاً لمدة سنة، وإرسال سياسة أمان محتوى (CSP — Content Security Policy) خاصة بكل تطبيق.
*في الشيفرة:* `Auth_UI/apps/console/public/web.config`؛ و`Auth_UI/apps/accounts/public/web.config`.

**ولا شيء في المستودع ينشر هذين المجلدين.** لا سكربت ولا ملف تعريف نشر ولا خط أنابيب يستهدف `apps/*/dist`. ورفع الملفات المبنية خطوة يدوية.

## 2. العمليتان ومصافحة البوابة

واجهة API والبوابة عمليتان منفصلتان على ASP.NET Core. والبوابة ليست زينة: هي المدخل الوحيد المقصود، وواجهة API ترفض فعلياً أي حركة لم تمر عبرها.

### الوكيل العكسي

البوابة مبنية على **YARP 2.3.0**. ومساراتها إعدادات خالصة — لا شيء يُسجَّل منها في الشيفرة. وعددها **24 مساراً**، وكلها تشير إلى عنقود واحد اسمه `auth-cluster`.

*في الشيفرة:* `Auth/API_Gateway/appsettings.json` (قسم `ReverseProxy`)؛ و`Auth/API_Gateway/Program.cs` السطران 110-111.

**قائمة المسارات قائمة سماح ترفض بالأصل، بمدخلة واحدة لكل ميزة.** فالمسار الذي لا يطابقه أي توجيه لا يُمرَّر إطلاقاً. وأنماط التوجيه تستخدم `v{version:int}`، فهي تطابق أي إصدار رقمي من API — أي أن *إصداراً* جديداً من API لا يحتاج تغييراً في البوابة، أما *ميزة* جديدة فتحتاجه.

| ‏المسارات | ‏سياسة محدد المعدل |
|---|---|
| ‏`/api/v{version:int}/auth/{**catch-all}` | ‏`auth` |
| ‏`users` و`roles` و`permissions` و`apikeys` و`applications` و`organizations` و`invitations` و`audit-logs` و`dashboard` و`images` و`webhookkeys` و`platform` و`notification-templates` و`notification-types` و`notification-layouts` و`notification-outbox` و`privacy-policy`، إضافة إلى `/privacy/{**catch-all}` و`/privacy` | ‏`api` (‏19 مساراً) |
| ‏`/api/v{version:int}/admin/{**catch-all}` | ‏`admin` |
| ‏`/.well-known/{**catch-all}` و`/openapi/{**catch-all}` و`/uploads/{**catch-all}` | ‏لا شيء — المحدد الشامل فقط |

**مسار واحد غائب عن قصد.** فالمسار `/api/v{version}/internal/gateway-settings` لا يُمرَّر، لأن البوابة تستدعيه مباشرة من خادم إلى خادم.

**ونقاط نهاية الصحة غائبة أيضاً عن قائمة السماح.** فالمساران `/health` و`/ready` في أي من العمليتين لا يمكن بلوغهما إلا بمخاطبة تلك العملية مباشرة. وهما غير قابلين للوصول عبر البوابة.

### ما الذي تضيفه البوابة إلى كل طلب مُمرَّر

| ‏السلوك | ‏الرأس |
|---|---|
| ‏يُضاف إلى كل طلب مُمرَّر، لكن فقط حين تكون قيمة `Gateway:Token` غير فارغة | ‏`X-Gateway-Token` |
| ‏تحويلات رؤوس التمرير القياسية | ‏`X-Forwarded-For` و`X-Forwarded-Host` و`X-Forwarded-Proto` |
| ‏يُحذف ثم يُعاد: قيمة المتصل إن وُجدت، وإلا فمعرّف GUID جديد | ‏`X-Correlation-ID` |

*في الشيفرة:* `Auth/API_Gateway/Program.cs` السطور 112-140.

### مصافحة الرمز

**ترفض واجهة API أي طلب لا يحمل رمز البوابة المتوقع.** والمقارنة ثابتة الزمن على البايتات الخام بعد فحص الطول، فهي لا تسرّب الرمز عبر التوقيت. وعدم التطابق ينتج **403** مع جسم `application/problem+json`.

وثلاثة أمور تخفف هذه القاعدة، وكلها مضبوطة في الإعدادات:

- `Gateway:ValidationEnabled` يوقف الفحص كلياً. قيمته `true` في الإعدادات الأساسية و**‏`false` في بيئة التطوير**، ولهذا يستطيع المطور استدعاء API مباشرة.
- `Gateway:ExemptPaths` يعدّد بادئات المسارات التي تتخطى الفحص. والقيمة المشحونة هي:
  `/.well-known/` و`/health` و`/ready` و`/swagger` و`/openapi` و`/uploads/`.
- `Gateway:TokenHeaderName` يسمّي الرأس. والبوابة تثبّت `X-Gateway-Token` في طرفها، فتغيير هذا المفتاح في طرف API وحده يكسر المصافحة.

ومدخلة فارغة داخل `ExemptPaths` كانت ستطابق كل طلب بالبادئة وتعطّل الإنفاذ بصمت على مستوى API كله. ولذلك تُتجاهل المدخلات الفارغة، ويثبّت اختبار مخصص هذا السلوك.
*في الشيفرة:* `Auth/Auth_API/Common/Middleware/GatewayTokenValidationMiddleware.cs` السطور 65-70 و87-115 و132-149؛ و`Auth/Auth_API.Tests/Middleware/GatewayExemptPathGuardTests.cs`.

### سحب الإعدادات

**البوابة لا تملك حدود معدلها ولا أصول CORS الخاصة بها.** بل تستجلبها من API وتطبّقها بحسب ختم الإصدار، فيغيّر المسؤولُ حداً من الكونسول فيتغير سلوك الحافة دون إعادة نشر البوابة. وفترة الاستجلاب الافتراضية 30 ثانية. وإذا فشل السحب احتفظت البوابة بآخر قيم معروفة لديها، وسجّلت ذلك مرة واحدة لكل انقطاع بدل تسجيله عند كل محاولة.
*في الشيفرة:* `Auth/API_Gateway/Configuration/GatewayRuntimeSettingsPoller.cs`.

### قاعدة الصيانة التي ينشئها هذا الترتيب

هناك اختبار في مجموعة اختبارات الواجهة الخلفية يُفشل البناء إذا وُجدت بادئة متحكم في API بلا مسار مقابل في البوابة. وهو موجود لأن الصور ولوحة المعلومات ومفاتيح Webhook شُحنت كلها بلا مسار، والعَرَض أن ميزة كاملة تعيد 404 دون ظهور أي خطأ في أي مكان.

**إذا أضفت متحكماً، فأضف مسار بوابة في التغيير نفسه.**
*في الشيفرة:* `Auth/Auth_API.Tests/Gateway/GatewayRouteCoverageTests.cs`.

## 3. تنفيذ الأمان

في هذا القسم كله، كل قيمة موسومة إما بأنها **مثبتة في الشيفرة** (قيمة حرفية في الكود لا يقرأها أي مفتاح إعدادات) وإما **قابلة للضبط**، ويُذكر معها مفتاح الإعداد بحالة الأحرف والتداخل الدقيقين.

### تجزئة كلمات المرور: Argon2id

يستخدم AuthSystem خوارزمية **Argon2id حصرياً** — الخوارزمية الموصى بها من OWASP والفائزة بمسابقة تجزئة كلمات المرور الدولية.

#### لماذا Argon2id دون البدائل الأخرى؟

| ‏القيد الرئيسي | ‏الحالة | ‏الخوارزمية |
|---|---|---|
| ‏قابلة للكسر في ثوانٍ | ‏**لا تُستخدم أبداً** | ‏MD5 |
| ‏سريعة جداً — لا مقاومة للقوة الغاشمة | ‏**ليست لكلمات المرور** | ‏SHA-256 |
| ‏تعتمد المعالج فقط — لا تقاوم هجمات معالجات الرسوميات بالفعالية نفسها | ‏**آمنة لكن تم تجاوزها** | ‏bcrypt |
| ‏تفتقر إلى صلابة الذاكرة؛ أضعف أمام الأجهزة الحديثة | ‏**آمنة لكن تم تجاوزها** | ‏PBKDF2 |
| ‏لا هجمات عملية معروفة عند ضبطها ضبطاً سليماً | ‏**المعيار الذهبي الحالي** | ‏**Argon2id** |

> تجمع Argon2id بين أفضل خصائص Argon2i (مقاومة هجمات القنوات الجانبية) وArgon2d (مقاومة الكسر بمعالجات الرسوميات). وهي تتطلب ذاكرة كبيرة لكل محاولة، مما يجعل هجمات تخمين كلمات المرور الجماعية غير مجدية اقتصادياً.

#### المعلمات

| ‏مفتاح الإعداد | ‏مثبتة في الشيفرة أم قابلة للضبط | ‏القيمة المشحونة | ‏المعلمة |
|---|---|---|---|
| ‏`Password:Argon2MemorySize` | ‏قابلة للضبط | ‏19,456 كيلوبايت (‏19 ميبي بايت) | ‏كلفة الذاكرة |
| ‏`Password:Argon2Iterations` | ‏قابلة للضبط | ‏2 | ‏التكرارات |
| ‏`Password:Argon2Parallelism` | ‏قابلة للضبط | ‏1 | ‏التوازي |
| ‏`Password:SaltSize` | ‏قابلة للضبط، وللقراءة فقط في الكونسول | ‏16 بايت من مولّد عشوائي آمن تشفيرياً | ‏طول الملح |
| ‏`Password:HashSize` | ‏قابلة للضبط، وللقراءة فقط في الكونسول | ‏32 بايت | ‏طول التجزئة |
| ‏— | ‏**مثبتة في الشيفرة** | ‏Argon2id، الإصدار المُرمَّز 19 | ‏الخوارزمية والإصدار |
| ‏— | ‏**مثبتة في الشيفرة** | ‏`CryptographicOperations.FixedTimeEquals` | ‏مقارنة التحقق |

ومعلمات Argon2 الثلاث كلها **تتطلب إعادة تشغيل**: فالمُجزِّئ يُبنى مرة واحدة كخدمة مفردة عند بدء التشغيل، ولذلك لا يُحدث تغييرها من الكونسول أي أثر حتى تُعاد العملية.

**التنسيق المخزَّن:** `$argon2id$v=19$m={memory},t={iterations},p={parallelism}[,keyid={id}]${salt}${hash}`

**إعادة التجزئة:** عند نجاح تسجيل الدخول بكلمة مرور، إذا اختلفت أي من المعلمات الثلاث عن الإعدادات الحالية — أو اختلف معرّف مفتاح الفلفل المخزَّن عن المطلوب — أُعيدت تجزئة كلمة المرور بالإعدادات الحالية وخُزّنت.

وتُعاد الاستفادة من Argon2id في أسرار أخرى يجري التحقق منها لا البحث عنها: مفاتيح API، ورموز الاسترداد للمصادقة الثنائية، وكلمات المرور لمرة واحدة للتحقق من البريد، ورموز التصعيد الموصوفة في القسم 15.

#### تحصين اختياري: الفلفل

**الفلفل سر من جانب الخادم يُمزج في كل تجزئة كلمة مرور.** تخيّل الملح مكوّناً خاصاً بكل مستخدم يُخزَّن بجوار التجزئة، والفلفل مكوّناً عاماً يُخزَّن في مكان ليس هو قاعدة البيانات.

- **ما الذي يدافع عنه.** اختراق قاعدة البيانات وحدها. فالتجزئات المسروقة لا يمكن كسرها بالقوة الغاشمة دون الفلفل، لأن الفلفل لا يعيش في قاعدة البيانات أصلاً.
- **كيف تُشغّله.** اضبط `Password:Pepper:Enabled` على `true`. وهو يُشحن **معطّلاً**.
- **ما الذي يكلّفه.** أول تشغيل بعد تفعيله يولّد 32 بايت من مادة المفاتيح ويحفظها في مخزن الأسرار. وإذا فشلت تلك الكتابة فشل بدء التشغيل — عن قصد.
- **ماذا يحدث إذا فقدته.** يفشل التحقق **فشلاً مغلقاً** لكل تجزئة تحمل معرّف ذلك المفتاح. لا «يتراجع» ولا «ينبّه» — أولئك المستخدمون لا يستطيعون تسجيل الدخول حتى يُستعاد المفتاح. انسخه احتياطياً تماماً كما تنسخ مفاتيح التوقيع.
- **كيف تُرحَّل التجزئات القائمة.** تُرقّى التجزئات غير المُفلفَلة بشفافية عند أول تسجيل دخول ناجح. وتُحفظ معرّفات الفلفل القديمة كي تظل تجزئاتها قابلة للتحقق.
- *مفاتيح الإعداد:* `Password:Pepper:Enabled` (يتطلب إعادة تشغيل)، و`Password:Pepper:CurrentKeyId`، و`Password:Pepper:Keys:{id}`. والأخيران يملكهما مخزن الأسرار ويجب ألا يظهرا في `appsettings.json` أبداً.

#### تحصين اختياري: فحص كلمات المرور المخترقة

**يمكن فحص كلمات المرور الجديدة مقابل مجموعة تسريبات Have I Been Pwned (‏HIBP).**

- **كيف يبقى الفحص خصوصياً.** لا يغادر الخادمَ سوى أول خمسة أحرف من تجزئة SHA-1 لكلمة المرور. وهذه خاصية عدم التمييز بين k عنصراً: تعيد الخدمة سلّة من اللواحق المرشحة، وتجري المقارنة محلياً.
- **كيف تُشغّله.** اضبط `Password:BreachedPasswordCheck:Enabled` على `true`. وهو يُشحن **معطّلاً**، ويتطلب إعادة تشغيل لأنه يغيّر أي عميل HTTP يُسجَّل.
- **ماذا يفعل عندما يعمل.** القيمة `Mode` إما `Enforce` (رفض كلمة المرور) وإما `Warn` (قبولها مع إعادة رأس استجابة `X-Password-Warning`). والافتراضي `Enforce`.
- **ماذا يفعل حين تتعذّر الخدمة.** القيمة `FailOpen` هي `true` افتراضياً، فتُقبل كلمة المرور. اضبطها على `false` كي يفشل الفحص فشلاً مغلقاً.
- **أين يُطبَّق.** التسجيل، وتغيير كلمة المرور، وإعادة تعيينها، وإنشاء المسؤول لمستخدم.
- *مفاتيح الإعداد:* `Password:BreachedPasswordCheck:Enabled` و`:Mode` و`:FailOpen` و`:RejectThreshold` و`:TimeoutMs`.

### سياسة كلمات المرور

| ‏مفتاح الإعداد | ‏القيمة المشحونة | ‏القاعدة |
|---|---|---|
| ‏`Password:MinimumLength` | ‏**8** (‏والافتراضي في الفئة 8 أيضاً؛ والكونسول يسمح بالمدى 6–128) | ‏الطول الأدنى |
| ‏`Password:RequireUppercase` | ‏true | ‏اشتراط حرف كبير |
| ‏`Password:RequireLowercase` | ‏true | ‏اشتراط حرف صغير |
| ‏`Password:RequireDigit` | ‏true | ‏اشتراط رقم |
| ‏`Password:RequireSpecialCharacter` | ‏true | ‏اشتراط رمز خاص |
| ‏**مثبتة في الشيفرة** | ‏`!@#$%^&*()-_=+[]{}\|;:'",.<>?/\` | ‏ما الذي يُعدّ رمزاً خاصاً |
| ‏**مثبتة في الشيفرة** | ‏`password` و`123456` و`qwerty` و`abc123` و`letmein` و`admin` و`welcome` و`monkey` و`dragon` و`master` و`login` | ‏السلاسل الممنوعة، بصرف النظر عن حالة الأحرف |
| ‏`Password:HistoryCount` | ‏**3** | ‏عمق سجل كلمات المرور |

**قواعد التركيب الخمس علنية.** ‏تعيد `GET /api/v1/Platform/password-policy` الطولَ الأدنى ومفاتيح فئات الأحرف الأربعة دون مصادقة، فتعرض نماذج التسجيل والدعوة وإعادة التعيين وتغيير كلمة المرور قائمة شروط حيّة أثناء الكتابة بدل أن يتعلّم الشخص القواعد رفضًا بعد رفض. ولا يُكشَف أي شيء آخر من هذا الجدول ولا من جدول القفل أدناه؛ فالسلاسل الممنوعة وفحص التسريب وفحص السجل تُحكم عند الإرسال فقط، ويعود كل سبب في مصفوفة `errors` في الاستجابة.

**سجل كلمات المرور يمنع أربع قيم لا ثلاثاً.** فالفحص يقارن المرشحة بتجزئات السجل المخزَّنة *وبكلمة المرور الحالية* أيضاً، فمع قيمة 3 في `HistoryCount` لا يستطيع المستخدم إعادة استخدام أي من كلمات مروره الأربع الأخيرة.

**لا توجد صلاحية منتهية لكلمات المرور.** فلا مسار تسجيل دخول يقيّم عمر كلمة المرور. وقد أُزيل المفتاح `Password:ExpirationDays` لأن لا شيء كان يحسبه. راجع القسم 19 للاطلاع على العمود الذي بقي بعده.

| ‏**مثبتة في الشيفرة** | ‏5 | ‏محاولات المصادقة الثنائية الفاشلة قبل القفل |
| ‏**مثبتة في الشيفرة** | ‏15 دقيقة | ‏مدة قفل المصادقة الثنائية |

ويُطبَّق القفل في جملة `UPDATE` واحدة في SQL تزيد عدّاد الإخفاقات، وعند بلوغ العتبة تضبط انتهاء القفل وحالة المستخدم معاً. ويفكّ الحساب قفله بنفسه عند أول محاولة تسجيل دخول بعد انقضاء نافذة القفل.

**وفحص البريد غير المؤكَّد يجري بعد التحقق من كلمة المرور، عن قصد** — فلو جرى قبله لأتاح لمهاجم أن يستدل على العناوين المسجَّلة.

### الجلسات

**الجلسات لا تنتهي بالخمول.** تنتهي الجلسة عند انتهاء رمز التحديث الخاص بها (‏7 أيام)، أو عند تسجيل المستخدم خروجه، أو عند إلغائها. والمفتاح `Session:IdleTimeoutMinutes` موجود في الإعدادات و**لا تقرأه أي شيفرة**؛ والأمر نفسه ينطبق على `Session:LifetimeHours` و`Session:ExtendOnActivity` و`Session:ExtensionHours`. أما مدة الجلسة الحقيقية فهي `Jwt:RefreshTokenLifetimeDays`.

**ولا يوجد جاهزاً أي سقف للجلسات المتزامنة.** فالمفتاح `Session:MaxConcurrentSessions` يُشحن بالقيمة `0`، ومعناها بلا حد. اضبطه على رقم موجب لفرض سقف. وما يحدث عند بلوغ السقف يتوقف على مفتاح ثانٍ:

- `Session:TerminateOldestOnMax` = `true` (‏الافتراضي) — تُنهى الجلسات الأقل استخداماً حديثاً ويمضي تسجيل الدخول الجديد. ويجري الإخلاء *بعد* كتابة صف الجلسة الجديدة، فتنجو جلسة الدخول الحالية دائماً.
- `Session:TerminateOldestOnMax` = `false` — **يُرفض** تسجيل الدخول الجديد قبل سكّ أي رمز، وتُسجَّل محاولة دخول فاشلة.

وهناك مفتاحا جلسة آخران يُقرآن ويعملان فعلاً: `Session:TerminateSessionsOnPasswordChange` و`Session:TerminateSessionsOnPasswordReset`، وكلاهما `true`، وكلاهما قابل للتجاوز لكل طلب.

### مصادقة الرموز: JWT بخوارزمية RS256

رمز الويب بصيغة JSON (‏JWT — JSON Web Token) رمز موقَّع يصف نفسه: تستطيع واجهة API الوثوق بمحتواه دون مراجعة قاعدة البيانات، لأن التوقيع يغطي ذلك المحتوى.

| ‏مفتاح الإعداد | ‏المدة | ‏ما هو | ‏نوع الرمز |
|---|---|---|---|
| ‏`Jwt:AccessTokenLifetimeMinutes` | ‏**15 دقيقة** | ‏رمز JWT موقَّع يحمل هوية المستخدم وصلاحياته | ‏**رمز الوصول — Access Token** |
| ‏`Jwt:RefreshTokenLifetimeDays` | ‏**7 أيام** | ‏64 بايتاً عشوائياً مُرمَّزة بـBase64. ولا يخزّن الخادم منه سوى تجزئة بمفتاح | ‏**رمز التحديث — Refresh Token** |

**ورمز التحديث ليس JWT وليس موقَّعاً.** إنه مادة عشوائية مبهمة، تُجزّأ بخوارزمية HMAC-SHA256 (‏رمز مصادقة رسالة قائم على التجزئة) قبل التخزين، فلا يمنح تسريبُ قاعدة البيانات رموزاً صالحة للاستعمال.

#### ما الذي يحتويه رمز الوصول فعلاً

| ‏متى تظهر | ‏المحتوى | ‏المطالبة |
|---|---|---|
| ‏دائماً | ‏معرّف المستخدم | ‏`sub` |
| ‏دائماً | ‏بريد المستخدم | ‏`email` |
| ‏دائماً | ‏معرّف GUID جديد لكل رمز | ‏`jti` |
| ‏دائماً | ‏وقت الإصدار بثواني Unix | ‏`iat` |
| ‏دائماً | ‏أسماء العرض | ‏`name` و`given_name` و`family_name` |
| ‏عند تزويد معرّف جلسة | ‏معرّف الجلسة — **ثابت عبر عمليات التحديث** | ‏`sid` |
| ‏عند ضبطها على المستخدم | ‏تفضيلات المستخدم | ‏`locale` و`timezone` و`theme` |
| ‏لكل دور | ‏مطالبة واحدة لكل رمز دور | ‏`roles` |
| ‏لكل صلاحية | ‏مطالبة واحدة لكل رمز صلاحية | ‏`permissions` |
| ‏لكل صلاحية عضوية في مؤسسة | ‏مطالبة واحدة لكل صلاحية مؤسسة، قيمتها `"{organizationId}:{code}"` | ‏`org_perm` |
| ‏دائماً | ‏المطالبات المسجَّلة القياسية | ‏`exp` و`nbf` و`iss` و`aud` |

**ومطالبة الجمهور ليست القيمة نفسها دائماً.** فالرمز المسكوك عبر تدفق رمز التفويض تكون `aud` فيه هي رمز *التطبيق*. أما في كل مسار آخر فهي القيمة الافتراضية للمنصة `Jwt:Audience`. وهذا مهم: الرمز المحصور بتطبيق **لا** يجتاز التحقق في `JwtTokenService.ValidateAccessToken`، لأن هذه الدالة تثبّت جمهور المنصة.

#### لماذا RS256 (غير متماثل) دون HS256 (متماثل)؟

</div>

```text
Symmetric (HS256):
  Same key to sign AND verify = must share secret with all verifiers

Asymmetric (RS256):
  Private key: Signs tokens (kept secret on auth server)
  Public key: Verifies tokens (safely distributed to any service)
  Result: Other services verify tokens without knowing the signing secret
```

<div dir="rtl" lang="ar">

مفتاح التوقيع هو RSA-2048. ومعالج رمز الحامل يثبّت قائمة الخوارزميات على `RS256` وحدها، فالرمز المقدَّم بخوارزمية أخرى يُرفض بدل أن يُخفَّض. وتسامح انحراف الساعة 60 ثانية (`Jwt:ClockSkewSeconds`، ويتطلب إعادة تشغيل).

#### تدوير رموز التحديث وكشف إعادة الاستخدام

**تدور رموز التحديث عند كل استعمال افتراضياً** (`Jwt:RotateRefreshTokens`). ويُوسم الرمز القديم بأنه مُلغى بالسبب `Rotated`، مع الإشارة إلى بديله.

**وتقديم رمز سبق تدويره يُعامَل على أنه سرقة.** فيلغي النظام كل رمز يملكه الحساب، وينشر حدث كشف إعادة الاستخدام، ويعيد خطأ. أما الرمز الذي أُلغي *بالجملة* (كأن يكون بتسجيل خروج من كل الأجهزة) فلا يُعامَل على أنه إعادة استخدام، عن قصد — بل يعيد خطأ «انتهت الجلسة» البسيط، لأن التبويب القديم الواحد كان سيتسبب لولا ذلك في إلغاء كامل للحساب.

#### إلغاء رمز سبق إصداره

يظل رمز الوصول صالحاً حتى انتهائه ما لم يُدرج في القائمة السوداء. وتدعم القائمة السوداء ثلاثة نطاقات: رمز واحد (`jti`)، وجلسة كاملة (`sid`)، وكل رمز يملكه مستخدم صدر قبل لحظة معينة.

**والقائمة السوداء قاموس داخل العملية تسنده جداول قاعدة البيانات.** يُكتب إليها عبر قناة، وتُعاد تعبئتها من `RevokedTokens` **عند بدء التشغيل**. ولا توجد إعادة قراءة دورية؛ والمؤقت الوحيد هو تمريرة تنظيف كل خمس دقائق. وأثر ذلك على تعدد النسخ مذكور في القسم 11.

### المصادقة الثنائية

**لا يوجد سوى كلمة المرور لمرة واحدة المعتمدة على الوقت (‏TOTP — Time-based One-Time Password) ورموز الاسترداد.** لا يوجد عامل ثانٍ عبر الرسائل القصيرة، ولا عامل ثانٍ عبر البريد. والسر المشترك مشفَّر في مكان تخزينه بالمفتاح الخاص بكل مستخدم الموصوف أدناه، ورموز الاسترداد مجزّأة بـArgon2id.

### تحديد معدل الطلبات

**هناك محدِّدان مستقلان، في عمليتين، بمفاتيح تقسيم مختلفة.** وقراءتهما كأنهما قائمة واحدة هي أشيع سوء فهم لهذا النظام.

#### واجهة Auth API (داخل العملية)

تعرّف واجهة API سياستين مسمّاتين فقط و**لا محدِّد شامل، عن قصد** — فقد أُزيلت سياسة عامة لأن لا نقطة نهاية كانت تستخدمها. وكلتا السياستين تقسّمان على عنوان IP للعميل المستخرج من `X-Forwarded-For`، مع الرجوع إلى عنوان المقبس.

| ‏مفاتيح الإعداد | ‏حد الانتظار | ‏النافذة | ‏المسموح | ‏السياسة |
|---|---|---|---|---|
| ‏`RateLimiting:LoginPermitLimit` و`RateLimiting:LoginWindowSeconds` | ‏0 | ‏60 ثانية | ‏**20** | ‏`login` |
| ‏`RateLimiting:PasswordResetPermitLimit` و`RateLimiting:PasswordResetWindowSeconds` | ‏0 | ‏60 ثانية | ‏**10** | ‏`password-reset` |

وسياسة `login` تغطي أكثر بكثير من تسجيل الدخول. فهي تُطبَّق أيضاً على التسجيل، وتسجيل الدخول الخارجي، ونقطة نهاية رمز OAuth، ونسيان كلمة المرور، وكل نقاط نهاية التحقق من البريد، وطلب حذف الحساب ونقاط تأكيده واستعادته، والتحقق من المصادقة الثنائية، ونقطتَي تحدي إدارة الأسرار، ونقطتَي الدعوة المجهولتين، ونقطتَي نهاية على متحكم المستخدمين. **ولذلك تتشارك هذه النقاط جميعها سلّة واحدة لكل عنوان IP**، وهو أمر يستحق المعرفة حين يصطدم اختبار أو سكربت بالرمز 429 دون توقّع.

**وغير محدودة المعدل على مستوى API إطلاقاً:** `POST /auth/refresh` و`POST /auth/revoke` و`GET /auth/authorize` و`POST /auth/introspect`، وكل نقاط نهاية إعداد المصادقة الثنائية وتفعيلها وتعطيلها.

#### بوابة API (الحافة)

تعرّف البوابة أربع سياسات، وتقسّم على عنوان **المقبس** بدل `X-Forwarded-For` — فهي الحافة، والوثوق بالرأس هناك كان سيتيح للمتصل اختيار قسم جديد مع كل طلب.

| ‏بادئة مفتاح الإعداد (تملكها واجهة API) | ‏حد الانتظار | ‏النافذة | ‏المسموح | ‏السياسة |
|---|---|---|---|---|
| ‏`GatewayRateLimiting:Global*` | ‏100، الأقدم أولاً | ‏60 ثانية | ‏1,000 | ‏المحدد الشامل |
| ‏`GatewayRateLimiting:Auth*` | ‏0 | ‏60 ثانية | ‏20 | ‏`auth` |
| ‏`GatewayRateLimiting:Api*` | ‏**10** | ‏60 ثانية | ‏100 | ‏`api` |
| ‏`GatewayRateLimiting:Admin*` | ‏0 | ‏60 ثانية | ‏120 | ‏`admin` |

وهذه الأرقام تعيش في **ثلاثة** مواضع يجب أن تتوافق: القيمة الافتراضية في سجل الإعدادات، وقسم `GatewayRateLimiting` في واجهة API، وقسم `RateLimiting` الخاص بالبوابة نفسها. واختبار تطابق يُفشل البناء إذا تباعدت، لأن التباعد غير مرئي أثناء التشغيل: يعرض الكونسول حداً بينما تنفّذ البوابة حداً آخر.

#### المضيفان يعيدان جسمين مختلفين للرمز 429

وهذا فخ تشغيل بيني حقيقي لكاتبي العملاء.

**رفض البوابة** — يضبط رأس استجابة `Retry-After` *ويعيد* أيضاً:

</div>

```json
{ "type": "...", "title": "...", "status": 429, "detail": "...", "retryAfter": 60 }
```

<div dir="rtl" lang="ar">

والقيمة `retryAfter` هنا عدد صحيح.

**رفض واجهة API** — **لا** يضبط رأس `Retry-After`، ويعيد:

</div>

```json
{ "error": "...", "retryAfter": 60.0 }
```

<div dir="rtl" lang="ar">

والقيمة `retryAfter` هنا عدد ثوانٍ بفاصلة عائمة.

**والعميل الذي يقرأ رأس `Retry-After` وحده لا يحصل على شيء من واجهة API**، وعليه أن يقرأ حقل JSON بدلاً منه.

### رؤوس الأمان

وسيط برمجي واحد يتشاركه المضيفان يكتب هذه الرؤوس على كل استجابة.

| ‏سلوك الكتابة فوقه | ‏القيمة | ‏الرأس |
|---|---|---|
| ‏يُكتب فوقه دائماً | ‏`DENY` | ‏`X-Frame-Options` |
| ‏دائماً | ‏`nosniff` | ‏`X-Content-Type-Options` |
| ‏دائماً | ‏`1; mode=block` | ‏`X-XSS-Protection` |
| ‏دائماً | ‏`strict-origin-when-cross-origin` | ‏`Referrer-Policy` |
| ‏**فقط حين لا يكون مضبوطاً مسبقاً** | ‏`default-src 'self'; frame-ancestors 'none'` | ‏`Content-Security-Policy` |
| ‏دائماً | ‏`geolocation=(), microphone=(), camera=()` | ‏`Permissions-Policy` |
| ‏— | ‏يُحذفان | ‏`Server` و`X-Powered-By` |

وهناك شرطان مهمان:

- **سياسة أمان المحتوى لا يُكتب فوقها أبداً.** فنقطة النهاية التي تضبط سياسة أمان محتوى خاصة بها هي التي تفوز. والنقاط التي تعيد HTML تعتمد على ذلك.
- **‏HSTS يُطبَّق خارج بيئة التطوير فقط.** وحين يُطبَّق تكون المدة القصوى 365 يوماً، مع `includeSubDomains` و`preload`.

*في الشيفرة:* `Auth/Auth.Shared/Http/SecurityHeadersMiddleware.cs`؛ و`Auth/Auth_API/Program.cs` السطور 889-898 و912-916.

### مشاركة الموارد عبر الأصول

تتحكم CORS في أصول المتصفح المسموح لها باستدعاء واجهة API. ومزوّد السياسة يعيد البناء من الإعدادات **الحية** ويخزّن النتيجة مؤقتاً ببصمة مأخوذة من قائمة الأصول مع علم بيانات الاعتماد، فيسري تغيير الأصول من الكونسول دون إعادة تشغيل.

- `Cors:AllowedOrigins` — قائمة الأصول الصريحة. والمدخلات الفارغة تُعامَل شواهدَ حذف وتُسقَط.
- `Cors:AllowCredentials` — يُشحن بالقيمة `true`.
- **يفشل بدء التشغيل خارج بيئة التطوير إذا كانت قائمة الأصول فارغة.**
- **والقيمة `"*"` لا تعني «اسمح بكل شيء».** بل تُعامَل على أنها «ليست قائمة صريحة»، وهو ما ينتج خارج بيئة التطوير سياسة **رفض شامل**.

### تشفير الحقول في مكان التخزين

هناك ثلاثة حقول مشفّرة في قاعدة البيانات بمفتاح فريد لكل مستخدم: سر TOTP، ورقم الهاتف، ورمز التحديث الخاص بالمزود الخارجي.

| ‏القيمة | ‏الخاصية |
|---|---|
| ‏AES-256-GCM | ‏الشِفرة |
| ‏`"v2:"` يتبعها ترميز Base64 لـ nonce ‖ tag ‖ ciphertext | ‏الحمولة المخزَّنة |
| ‏12 / 16 / 32 بايت | ‏أحجام nonce والوسم والمفتاح |
| ‏`"{purpose}:{userId}"` | ‏البيانات الإضافية المصادَق عليها |
| ‏مفتاح تشفير البيانات الخاص بكل مستخدم (‏DEK — Data Encryption Key) محمي بدوره بحلقة مفاتيح حماية البيانات | ‏تغليف المفتاح |
| ‏داخل العملية، بانتهاء منزلق مدته 15 دقيقة | ‏ذاكرة المفتاح المفكوك المؤقتة |

**والبيانات الإضافية المصادَق عليها تعني أن النص المشفَّر يفشل فشلاً مغلقاً إذا نُقل.** فانسخ قيمة مشفَّرة إلى صف مستخدم آخر أو إلى عمود آخر، وسيفشل فك التشفير بدل أن يعيد نصاً صريحاً خاطئاً.

**ولا تُستخدم ميزة Always Encrypted في SQL Server.** فلا عمود في المخطط مُعلن بـ`ENCRYPTED WITH`. والحماية كلها من جانب التطبيق. وقد تحمل سلسلة اتصال منشورة العلم `Column Encryption Setting=Enabled`؛ وهذا العلم بلا أثر هنا.

## 4. قدرات مزود الهوية

**‏AuthSystem هو بالفعل خادم تفويض عامل بمعيار OAuth 2.0.** ‏وهذا سلوك مشحون في المنتج اليوم، لا بنداً في خارطة طريق: فأي تطبيق من طرف ثالث يستطيع أن يسجّل به دخول المستخدمين الآن.

**‏لكنه ليس بعدُ مزوّد هوية بمعيار OpenID Connect (اختصاراً OIDC)، وهذا القسم لا يدّعي أنه كذلك.** ‏فهو لا يصدر `id_token`، وهو الشيء الوحيد الذي يضيفه OIDC فوق OAuth 2.0. أما الذي يستعيره من OIDC فهو عُرف الاكتشاف — أي مسارات `/.well-known/` الثابتة الموصوفة أدناه — كي تستطيع مكتبة عميل أن تجد نقطة نهاية الرموز ومفتاح التوقيع العام دون أن يُخبرها أحد. ومكتبة عميل OIDC موجَّهة إلى هذا النظام ستُتمّ تبادل الرمز ثم لا تجد `id_token` ينتظرها. ووثيقة الاكتشاف مكتوبة لتشير إلى ذلك بالضبط، وهذا الإغفال مقصود لا سهو.

### التدفق

التدفق الوحيد المدعوم هو **رمز التفويض مع PKCE** (‏Proof Key for Code Exchange — مفتاح إثبات لتبادل الرمز). ومعنى PKCE أن العميل يولّد مُتحقِّقاً عشوائياً، ولا يرسل في البداية إلا تجزئته، ثم يثبت حيازته للأصل عند استبدال الرمز — فيصير الرمز المعترَض بلا فائدة.

| ‏مثبَّت في الشيفرة أم قابل للضبط | ‏القيمة | ‏الحقيقة |
|---|---|---|
| ‏— | ‏`GET /api/v1/auth/authorize`، بلا مصادقة، و**بلا سياسة تحديد معدل** | ‏نقطة نهاية التفويض |
| ‏— | ‏`POST /api/v1/auth/token`، بلا مصادقة، على سياسة تحديد المعدل `login`، ومُرمَّزة على هيئة نموذج | ‏نقطة نهاية الرمز |
| ‏مثبَّت في الشيفرة | ‏`authorization_code` و`refresh_token` — وما عداهما يُرفض | ‏المنح المدعومة |
| ‏— | ‏**لا شيء** — عملاء عامّون فقط، وPKCE إلزامي | ‏مصادقة العميل |
| ‏مثبَّت في الشيفرة | ‏`code` وحدها | ‏قيمة `response_type` المقبولة |
| ‏مثبَّت في الشيفرة | ‏**`S256` وحدها** — و`plain` مرفوضة | ‏قيمة `code_challenge_method` المقبولة |
| ‏مثبَّت في الشيفرة | ‏`^[A-Za-z0-9\-._~]{43,128}$` | ‏صيغة المُتحقِّق والتحدي |
| ‏مثبَّت في الشيفرة | ‏512 محرفاً | ‏الطول الأقصى لـ`state` |
| ‏`IdentityProvider:AuthorizationCodeLifetimeSeconds` | ‏**60 ثانية** | ‏عمر رمز التفويض |
| ‏— | ‏64 بايتاً عشوائياً، تُخزَّن على هيئة تجزئة HMAC-SHA256 | ‏مادة الرمز |
| ‏— | ‏معرّف التطبيق، ومعرّف المستخدم، وعنوان إعادة التوجيه بالضبط، والتحدي، وعنوان IP للعميل | ‏ارتباطات الرمز |
| ‏— | ‏ذرّي ولمرة واحدة؛ والمحاولة الثانية تُسجَّل بوصفها إعادة تشغيل | ‏استهلاك الرمز |
| ‏— | ‏ترميز Base64-URL لتجزئة SHA-256 للمُتحقِّق، وتُقارَن في زمن ثابت | ‏التحقق من PKCE |

**وحالات الفشل تنقسم قسمين، عن قصد.** فمعرّف العميل `client_id` المجهول أو غير النشط، أو عنوان إعادة توجيه غير مسجَّل لذلك التطبيق، يعيد **الرمز 400 دون أي إعادة توجيه** — فالنظام لا يقذف مستخدماً إلى موضع لم يُتحقَّق منه. وكل ما عدا ذلك يعيد التوجيه إلى العنوان المسجَّل، حاملاً رمز خطأ OAuth وقيمة `state` الأصلية.

### تسجيل الدخول الموحّد عبر التطبيقات

بعد نجاح تسجيل الدخول تضبط واجهة API ملف تعريف جلسة، فإذا جاء لاحقاً نداء `/authorize` لتطبيق *مختلف* أعادت استخدام ذلك الملف بدل أن تطالب المستخدم من جديد.

| ‏القيمة | ‏الخاصية |
|---|---|
| ‏**`auth_idp`** (‏`IdentityProvider:IdpSessionCookieName`، ويتطلب إعادة تشغيل) | ‏اسم ملف التعريف |
| ‏`true` و`true` و`Lax` — وكلها مثبَّتة في الشيفرة | ‏`HttpOnly` و`Secure` و`SameSite` |
| ‏**غير مضبوط** — فملف التعريف مقصور على المضيف، ولا يكون قط ملف تعريف لنطاق أعلى | ‏`Domain` |
| ‏7 أيام (‏`IdentityProvider:IdpSessionLifetimeDays`) | ‏العمر المطلق |
| ‏صف في جدول `IdpSessions` لا يخزّن إلا تجزئة HMAC-SHA256 للرمز | ‏السجل على جانب الخادم |
| ‏الرمز موسوم بـ`[JsonIgnore]`؛ والمتحكم وحده ينقله إلى ملف التعريف | ‏لا يظهر قط في جسم استجابة |

**وإعادة المصادقة المشدَّدة مدعومة.** فالمعامل `prompt=login` يفرض تسجيل دخول جديداً دائماً؛ وفيما عدا ذلك تُقارَن الأصغر من قيمتَي `ReauthenticationMaxAgeMinutes` الخاصة بالتطبيق و`max_age` الواردة في الطلب بعمر ملف تعريف الجلسة. وتُقيَّم هذه المشدَّدة **قبل** فحص أهلية التطبيق، عن قصد، حتى لا يُستعمل ملف تعريف قديم في استكشاف التطبيقات التي يبلغها المستخدم.

### الاكتشاف

ثلاث نقاط نهاية خارجة عن نظام الإصدارات وبلا مصادقة، لأن مواصفة OIDC تشترط مسارات ثابتة.

| ‏ما الذي تعيده | ‏المسار |
|---|---|
| ‏وثيقة الاكتشاف | ‏`GET /.well-known/openid-configuration` |
| ‏مجموعة مفاتيح الويب بصيغة JSON (‏JWKS) — أي مفتاح التوقيع العام | ‏`GET /.well-known/jwks.json` |
| ‏المفتاح نفسه في صورة نص PEM | ‏`GET /.well-known/public-key.pem` |

وتعلن وثيقة الاكتشاف ما هو منفَّذ بالضبط: `response_types_supported = ["code"]`، و`grant_types_supported = ["authorization_code","refresh_token"]`، و`code_challenge_methods_supported = ["S256"]`، و`token_endpoint_auth_methods_supported = ["none"]`. وهي لا تدّعي خوارزمية توقيع لـ`id_token`، ولا تعلن نطاقات، لأن كليهما غير منفَّذ.

**ومجموعة المفاتيح تنشر مفتاحاً واحداً بالضبط.** وانظر القسم 15 لتعرف ما يعنيه ذلك للتدوير.

## 5. نموذج التفويض

### كيف تُحرَس نقطة النهاية

تعلن نقطة النهاية الصلاحية التي تحتاجها في صورة سمة. وهذه السمة ليست سياسة ثابتة — بل هي اسم سياسة، ومزوّد السياسات يبني السياسة عند الطلب لكل اسم يبدأ بـ`Permission:`.

</div>

```text
[RequirePermission("users:read")]
   -> policy name "Permission:users:read"
      -> RequireAuthenticatedUser() + PermissionRequirement("users:read")
         -> handler reads the "permissions" claims off the JWT
```

<div dir="rtl" lang="ar">

**والفحص يعتمد على المطالبات وحدها في صلاحيات المنصة — بلا أي نداء لقاعدة البيانات.** فالصلاحيات موجودة أصلاً داخل الرمز.

### دلالات محرف البدل

محرف البدل **مطابقة بادئة**، وحدّه هو النقطتان الرأسيتان `:`.

1. الصلاحية الحرفية `*` تمنح كل شيء.
2. المطابقة التامة تمنح، دون تفريق بين حالة الأحرف.
3. الصلاحية المملوكة المنتهية بـ`:*` تطابق حين يبدأ الرمز المطلوب بتلك البادئة متبوعةً بنقطتين رأسيتين، أو حين يساوي البادئة تماماً.

**فـ`crm:*` تطابق `crm:leads:read` وتطابق `crm`، لكنها لا تطابق `crmx:read`.** أما محرف البدل في وسط النص، مثل `a:*:c`، فغير مدعوم.

**والفخ الذي ينشئه هذا:** الصلاحية `auth:users:*` **لا** تفي بالمتطلب `users:read`. فهما بادئتان مختلفتان.

### نطاق المؤسسة

المؤسسات سياق محدود مشحون في المنتج، له 26 حالة استخدام و7 جداول خاصة به.

- يحمل الرمز مطالبة `org_perm` واحدة لكل زوج (مؤسسة، صلاحية)، وقيمتها `"{organizationId}:{code}"`، وتُقسَم عند أول نقطتين رأسيتين فقط.
- ولا ينطلق مسار الرجوع إلى قاعدة البيانات إلا حين يبدأ الرمز المطلوب بـ`org:` **و** يحمل الطلب في مساره قيمة تسمّي المؤسسة (`orgId`، وإلا `id`).
- **وحين لا يحمل الرمز أي مطالبة `org_perm` لتلك المؤسسة**، تُجرَّب قراءة حية واحدة من قاعدة البيانات لصلاحيات عضوية المستدعي. وهذا يغطي مؤسسة أُنشئت أثناء الجلسة الحالية ولم تدخل صلاحياتها الرمز بعد. أما إن كان الرمز يحمل *بعض* المطالبات لتلك المؤسسة دون المطالبة المطلوبة، فلا تُجرى **أي** قراءة ويُرفض الطلب.
- ثمانية رموز صلاحيات للمؤسسات مستعملة: `org:update`، و`org:members:read`، و`org:members:manage`، و`org:members:invite`، و`org:apps:read`، و`org:apps:manage`، و`org:permissions:read`، و`org:permissions:manage`.
- وثلاثة أدوار عضوية مدمجة موجودة: `org-owner` (ويحمل `org:*`)، و`org-admin`، و`org-member`.

### فجوة التزويد بالبيانات الأولية — اقرأ هذا قبل تصميم الأدوار

**تُفرَض 50 رمز صلاحية مميزاً عبر 138 استعمالاً للسمة. أما النشر النظيف لقاعدة البيانات فيزوّدها بـ45 صف صلاحية و8 أدوار — و34 رمزاً من الـ50 المفروضة لا صف لها على الإطلاق.**

وستة من هذه الرموز الأربعة والثلاثين لا وجود لها في **أي ملف SQL في المستودع كله**، فلا سبيل إلى منحها إلا بكتابة صفوفها باليد:

</div>

```text
apikeys:validate  webhookkeys:create  webhookkeys:read
webhookkeys:revoke  webhookkeys:rotate  webhookkeys:validate
```

<div dir="rtl" lang="ar">

ويوجد ملف تزويد كان سيوفّر 28 رمزاً من الأربعة والثلاثين — وهو `08_AdditionalPermissions.sql` الذي يحمل 47 رمزاً — لكن **نص ما بعد النشر لا يضمّه أبداً**، فلا يعمل في نشر نظيف.

والنتائج العملية:

- **«أنشئ دوراً وامنحه `users:read`» أمر متعذّر على نشر نظيف.** فلا يوجد صف من هذا القبيل ليُمنح.
- **والحساب الوحيد الذي يبلغ تلك النقاط هو `super-admin`،** عبر صلاحيته الشاملة `*`.
- **والأدوار المزوَّدة `admin` و`auditor` و`user-manager` لا تستطيع إدارة النظام.** فهي تحمل رموزاً ببادئة `auth:`، ولأن محرف البدل مطابقة بادئة، فإن `auth:users:*` لا تفي بالمتطلب `users:read`.

والأدوار الثمانية المزوَّدة هي `super-admin` و`admin` و`user-manager` و`auditor` و`user` و`org-owner` و`org-admin` و`org-member`.

| ‏ | ‏**52** | ‏**المجموع** |

### الوصول إلى البيانات

**مكتبة Dapper فوق SQL مكتوب باليد هي آلية الوصول الوحيدة إلى البيانات.** فلا يوجد مُخطِّط علاقات كائنية (ORM — Object-Relational Mapper) يولّد الاستعلامات نيابةً عن المطور، ولا متتبّع تغييرات، ولا محرك هجرات. و39 ملفاً من أصل 44 في مجلد التخزين `Persistence` تستعمل Dapper مباشرة.

- **تسعة إجراءات مخزَّنة معرَّفة، ولا يُستدعى منها إلا أربعة.** والأربعة هي `sp_GetUserById` و`sp_GetUserByEmail` و`sp_CreateRefreshToken` و`sp_RevokeAllUserTokens`. وتُستدعى بوصفها نص `EXEC`، لا عبر `CommandType.StoredProcedure` قط. أما الخمسة الباقية — ومنها `sp_ValidateCredentials` و`sp_ValidateRefreshToken` اللذان يوحي اسماهما بأنهما في قلب النظام — فلا يستدعيها شيء.
- **وجُمل SQL مكتوبة خصيصاً لـSQL Server.** معرّفات بين أقواس معقوفة، وعمليات دمج `MERGE`، ودالة `DATEADD`، ونداءات `EXEC` الأربعة. والنقل إلى محرك آخر يعني إعادة كتابة المستودعات الـ41 ومشروعَ قاعدة البيانات، لا استبدال تنفيذ واحد.
- **ومصنع الاتصالات يعيد اتصالاً مفتوحاً أصلاً.** فاستدعاء `Open()` عليه يرمي استثناءً، ويظهر الإخفاق في صورة استجابة HTTP 400 محيّرة بدل خطأ واضح.
  *في الشيفرة:* `Auth/Auth.Infrastructure/Persistence/SqlConnectionFactory.cs` الأسطر 22-24.
- **والترتيب محصور في قائمة سماح.** فكل نقطة نهاية تعرض قائمة تقبل `sortBy` و`sortDirection`، وأسماء الحقول المقبولة ثوابت في طبقة النطاق. والقيمة غير المعروفة تعيد 400 بدل أن تبلغ SQL.

### شكل نموذج النطاق

- 51 فئة كيان، **ثمانية منها فقط جذور تجميعات**: `Application` و`NotificationLayout` و`NotificationTemplate` و`NotificationType` و`Organization` و`Permission` و`Role` و`User`.
- **ولا توجد إلا ثلاثة كائنات قيمة**: `Email` و`PermissionCode` و`PhoneNumber`. لكل واحد منها مُنشئ خاص، ومصنع `Create` يتحقق من القيمة ويعيد `ErrorOr<T>`، ومصنع `From` بلا تحقق لا يُستعمل إلا عند إعادة تكوين الكائن من قاعدة البيانات.
- و21 فهرساً ساكناً للأخطاء تزوّد أخطاء النطاق كلها؛ والمعالجات تعيدها بدل أن ترمي استثناءات.

### كيف يُنشَر المخطط

مشروع قاعدة البيانات مشروع SSDT يُبنى إلى ملف **DACPAC** (حزمة تطبيق طبقة البيانات — Data-tier Application Package)، وهو ملف واحد يصف المخطط المطلوب. ونشرُه يقارن ذلك الوصف بقاعدة البيانات الحية ثم يولّد نص التغيير.

**ولا توجد نصوص تراجع.** فمجلد الترقيات يحمل 9 نصوص أمامية الاتجاه فقط، وتكرار تنفيذها لا يضيف أثراً جديداً. والتراجع يعني استعادة نسخة احتياطية.

**وليس كل ما في المجلدات يعمل.** فمن أصل 16 نص تزويد على القرص يضمّ نصُّ ما بعد النشر عشرة؛ ومن أصل 9 نصوص ترقية يضمّ خمسة. والنصوص الستة غير الموصولة تشمل `08_AdditionalPermissions.sql`، وهو الذي كان سيسدّ فجوة الصلاحيات المذكورة في القسم 5.

## 7. الأنظمة الفرعية والعمل في الخلفية

### الإشعارات

**كل محتوى الإشعارات يسكن في قاعدة البيانات، لا في ملفات موارد ولا في الشيفرة.** فالمسؤول يحرّر القوالب من الكونسول؛ ولا يحتاج تغييرُ رسالة بريد إلى إعادة نشر.

| ‏القيمة | ‏الحقيقة |
|---|---|
| ‏**16** | ‏أنواع الإشعارات المزوَّدة |
| ‏**15** — و`welcome-email` هو النوع المزوَّد الوحيد الذي **لا** قالب له | ‏القوالب المزوَّدة |
| ‏**105** (‏15 قالباً × 7 لغات) | ‏صفوف الترجمة |
| ‏**1** | ‏التخطيطات المزوَّدة |

**والإرسال مصفوف في صندوق صادر افتراضياً.** فقيمة `Notifications:UseOutbox` هي `true`، فيكتب المعالج صفاً ثم يعود؛ ويستولي موزّع خلفي على دفعة ويرسلها. ويستطلع الموزّع كل 30 ثانية (`Notifications:PollIntervalSeconds`)، ويستولي على 20 صفاً في المرة الواحدة (`Notifications:BatchSize`)، ويعيد المحاولة حتى 5 مرات (`Notifications:MaxAttempts`) قبل أن ينقل الصف إلى الرسائل الميتة، ويستردّ الصفوف العالقة أكثر من 5 دقائق (`Notifications:StaleClaimMinutes`).

### التوطين

**سبع لغات على الجانبين، وهي السبع نفسها.** الإنجليزية والعربية والتركية والفرنسية والصينية والأردية والفارسية — ورموزها `en` و`ar` و`tr` و`fr` و`zh` و`ur` و`fa`. والعربية والأردية والفارسية تُكتب من اليمين إلى اليسار.

وفي الواجهة الخلفية أربع عائلات موارد — رسائل التطبيق، وأخطاء النطاق، ورسائل الوسائط البرمجية، ورسائل التحقق — لكل عائلة منها ملف إنجليزي محايد واحد وستة ملفات ثقافات. وتُختار لغة الاستجابة بترتيب الأولوية هذا: **سلسلة الاستعلام ← ملف تعريف الارتباط ← ترويسة `Accept-Language` ← الترويسة المخصصة `X-Language`.** والقيمة غير المدعومة في الترويسة المخصصة تُرفض بدل أن تُقبل بصمت.

### حذف الحساب

الحذف الذي يبدأه المستخدم عملية مجدولة قابلة للاسترجاع، لا محواً فورياً: مهلة سماح (`AccountDeletion:GraceDays`، وقدرها 30 يوماً) يستطيع المستخدم خلالها استرجاع حسابه، ثم خطوة تأكيد بكلمة مرور لمرة واحدة، ثم تنفيذ لا رجعة فيه يتولاه عامل خلفي. والمعرّفات المُتلَفة تُسجَّل بصيغة بصمات في سجل حجز، حتى لا يتمكن شخص آخر من إعادة تسجيل عنوان محذوف على الفور؛ ومدة الحجز مشتقة من أطول السجلات عمراً المرتبطة بذلك العنوان.

**والمفتاح الذي يبصم تلك المعرّفات دائم.** فتدويره يكسر السجل. والقسم 15 يذكره صراحةً.

### إعدادات النظام

**الإعدادات مرتّبة طبقات، وجزء منها حيّ.** فجدول في قاعدة البيانات يحمل تجاوزات متفرقة يجلس فوق ملفات الإعدادات، ويحمّله مزوّد إعدادات مخصص، ويُحرَّر من كونسول الإدارة. وتُستهلك الإعدادات عبر `IOptionsSnapshot`/`IOptionsMonitor`، فيسري معظمها دون إعادة تشغيل. وثمة سجلّ يحدد أي الحقول يتطلب إعادة تشغيل، ويعرض الكونسول حالة «بانتظار إعادة التشغيل» لتلك الحقول. والقسم 17 يعرض سلسلة الأسبقية كاملةً وقائمة ما يتطلب إعادة التشغيل.

## 8. بنية الأداء

**لا يوجد في هذا المستودع أي قياس أداء مرجعي، ولا اختبار حِمل، ولا أي ناتج لتحليل أداء.** فقرارات التصميم المذكورة أدناه حقيقية، وأما أي رقم يُلصق بها فلن يكون كذلك. ولذلك يذكر هذا القسم القرارات وآلياتها، لا أرقاماً مقيسة.

### 1. مكتبة Dapper: تنفيذ SQL مباشر

بدلاً من ORM كامل يولّد جُمل SQL بنفسه، يستخدم AuthSystem **Dapper** — وهو Micro-ORM يُسقِط صفوف النتيجة على كائنات، ويترك كتابة SQL لك.

| ‏Dapper (‏Micro-ORM) | ‏ORM كامل (مثل Entity Framework) | ‏الجانب |
|---|---|---|
| ‏SQL مكتوب باليد وصريح | ‏SQL مولَّد تلقائياً، وقد يكون غير فعال | ‏تنفيذ الاستعلام |
| ‏ضئيل (بلا تتبّع) | ‏أعلى (تتبّع الكائنات واكتشاف التغييرات) | ‏عبء الذاكرة |
| ‏تحكم كامل | ‏مُجرَّد بعيداً عن المطور | ‏التحكم في SQL |
| ‏مباشر وشفاف | ‏تجريد أعلى | ‏التعقيد |

وهذا الجدول هو مسوّغ الاختيار لا أكثر. **وEntity Framework ليس تبعية لهذا النظام، ولا يظهر فيه في أي موضع** — وإنما ذُكر هنا بوصفه خط المقارنة المرجعي وحده.

وتكلفة هذا الاختيار مذكورة بصراحة في القسم 6: فكل استعلام مكتوب خصيصاً لـSQL Server، ولا توجد قابلية نقل بين محركات قواعد البيانات.

### 2. نمط Async/Await: عمليات غير محجوبة

كل استدعاء لقاعدة البيانات غير متزامن، ويقبل `CancellationToken`. والطلب الذي يتخلى عنه العميل يُلغى بدل أن يُنفَّذ حتى نهايته؛ ووسيطة معالجة الاستثناءات تتعرف على هذه الحالة فلا تكتب استجابة.

### 3. تجميع الاتصالات — Connection Pooling

تُجمِّع ADO.NET الاتصالات لكل نص اتصال على حدة، فيعيد استدعاءُ المستودع استخدامَ اتصال مادي مفتوح بدل دفع كلفة مصافحة جديدة.

**وانتبه إلى العُرف المتّبع هنا:** الدالة `SqlConnectionFactory.CreateConnectionAsync` تعيد اتصالاً **مفتوحاً أصلاً**. فعلى المستدعي ألا يستدعي `Open()` مرة أخرى.

### 4. التخزين المؤقت في الذاكرة

التخزين المؤقت داخل العملية بالكامل. لا يوجد خادم تخزين مؤقت، ولا أي تجريد لذاكرة مؤقتة موزَّعة.

| ‏مدة الصلاحية | ‏ما الذي تحتفظ به | ‏الذاكرة المؤقتة |
|---|---|---|
| ‏مدخلات مستوى المستخدم تُحفظ ساعة واحدة بعد الإلغاء؛ وتمريرة تنظيف كل 5 دقائق | ‏مدخلات الرموز والجلسات والمستخدمين الملغاة | ‏القائمة السوداء للرموز |
| ‏تُبطَل عند نشر قالب | ‏قوالب الإشعارات بعد عرضها | ‏`TemplateCache` |
| ‏محدودة بـ1,024 مدخلة؛ ولا انتهاء زمني لها | ‏قوالب Liquid المحلَّلة سلفاً، مفهرسةً بنصّ مصدرها بالضبط | ‏الذاكرة المؤقتة للتحليل في `FluidTemplateRenderer` |
| ‏تُبطَل عند النشر | ‏نواتج عرض سياسة الخصوصية | ‏`PolicyArtifactCache` |
| ‏انتهاء منزلق مدته 15 دقيقة | ‏مفاتيح تشفير البيانات بعد فك تغليفها | ‏الذاكرة المؤقتة لمفاتيح كل مستخدم |

**وفحوص الصلاحيات غير مخزَّنة مؤقتاً، لأنها لا تحتاج إلى ذلك.** ففحص صلاحية نقطة النهاية يقرأ مطالبة `permissions` من رمز سبق التحقق منه، دون أي إدخال أو إخراج على الإطلاق. والاستثناء الوحيد هو الرجوع إلى المؤسسة الموصوف في القسم 5، إذ ينفّذ استعلام قاعدة بيانات حياً مع كل طلب حين لا يحمل الرمز مطالبات تخص تلك المؤسسة.

### الإعدادات لا "تُحمَّل عند بدء التشغيل" وكفى

فوق الملفات طبقة تجاوزات في قاعدة البيانات، تُحدَّث عند الطلب وعلى مؤقت مدته 5 دقائق معاً، ومعظم الإعدادات تُقرأ عبر واجهات لقطة. والقسم 17 يعرض سلسلة الأسبقية، ويسمي الإعدادات التي تتطلب إعادة تشغيل فعلاً.

### تصميم RESTful

| ‏التنفيذ | ‏المبدأ |
|---|---|
| ‏`/users` و`/roles` (لا `/getUsers`) | ‏**الموارد أسماء لا أفعال** |
| ‏GET (قراءة) وPOST (إنشاء) وPUT (تحديث) وDELETE (حذف) | ‏**أفعال HTTP للإجراءات** |
| ‏كل طلب يحمل كل ما يلزمه من معلومات — رمز الحامل | ‏**بلا حالة** |
| ‏`/api/v1/{resource}/{id}/{sub-resource}` | ‏**الشكل الرئيسي للعنوان** |

**وثلاث عائلات من المسارات تخرج عن هذا الشكل عن قصد**، وكاتب العميل يحتاج إلى معرفتها جميعاً:

1. **نقاط نهاية الإدارة** تقع تحت مقطع إضافي: `/api/v1/admin/platform-settings` و`/api/v1/admin/system-settings` و`/api/v1/admin/Secrets`.
2. **سياسة الخصوصية العامة** بلا إصدار، وخارج `/api` كلياً: `/privacy`.
3. **نقاط نهاية الاكتشاف** بلا إصدار بحكم المواصفة: `/.well-known/*`.

ومطابقة العناوين لا تفرّق بين حالة الأحرف، فـ`/api/v1/users` و`/api/v1/Users` يصلان إلى الإجراء نفسه.

### إصدار API

**يوجد إصدار واحد فقط: `v1`.** ولا يوجد متحكم من إصدار ثانٍ في أي موضع من الشجرة.

- المسارات تحمل الإصدار مقطعاً داخل العنوان. وقالب المسار في كل متحكم مُصدَّر يشترط هذا المقطع حرفياً، ولذلك **فالعنوان هو ما يختار الإصدار فعلاً**.
- سُجِّلت ثلاث قارئات للإصدار — مقطع العنوان، ورأس `X-Api-Version`، ومعامل الاستعلام `api-version` — لكن قارئ الرأس وقارئ الاستعلام لا يستطيعان اختيار إصدار بمفردهما، لأن قالب المسار يفرض وجود المقطع.
- الإصدار الافتراضي هو `1.0`، ويُفترض حين لا يُذكر، والاستجابة تُبلِّغ بالإصدارات المدعومة.
- **ومتحكمان يقعان خارج نظام الإصدارات كلياً:** متحكم الاكتشاف (مُعلَن أنه محايد تجاه الإصدار، لأن OIDC يشترط مسارات ثابتة)، ومتحكم السياسة العامة (الموجَّه إلى `/privacy`).

### عزل الوصول إلى قاعدة البيانات

المستودعات وحدها تتحدث إلى قاعدة البيانات، و`Auth.Infrastructure` وحده يحتوي على المستودعات.

WRONG:

Handler    -> Dapper directly (bypassing the repository)

## 10. مبادئ التصميم

### مبدأ DRY — لا تكرر نفسك

المنطق المشترك مُجمَّع في خدمات قابلة لإعادة الاستخدام. فتجزئة كلمات المرور موجودة في موضع واحد (`Argon2PasswordHasher`)، ويستعملها تسجيل الدخول والتسجيل والتحقق من مفاتيح API والتحقق من رموز الاسترداد وتحدي رفع المستوى. والخطأ الذي يُصلَح هناك يُصلَح في كل مكان.

### مبادئ SOLID

| ‏التطبيق في AuthSystem | ‏المبدأ |
|---|---|
| ‏معالج واحد لكل حالة استعمال — 190 معالجاً، لكل واحد مجلده الخاص مع أمره ومدقّقه | ‏**المسؤولية الواحدة** |
| ‏تُضاف مزودات الهوية الخارجية وقنوات الإشعار الجديدة بتسجيل استراتيجية جديدة في مصنع مُفهرَس، دون أي تغيير في الشيفرة التي تحلّها | ‏**مفتوح/مغلق** |
| ‏تنفيذات المستودعات قابلة للاستبدال خلف واجهاتها، وهو ما يجعل المعالِجات قابلة للاختبار بالمحاكيات. **لكنه لا يجعل محرك قاعدة البيانات قابلاً للاستبدال** — فكل مستودع يحوي SQL خاصاً بـSQL Server | ‏**استبدال ليسكوف** |
| ‏واجهات المستودعات واحدة لكل تجميعة — 39 واجهة — فيعتمد المعالج على عقد تجميعة واحدة بدل واجهة وصول بيانات جامعة. **ولا يوجد فصل منفصل بين القراءة والكتابة** | ‏**فصل الواجهات** |
| ‏الواجهات مُعلَنة في `Auth.Domain` و`Auth.Application`، والتنفيذات تعيش في `Auth.Infrastructure` وتُربط بحقن التبعيات عند بدء التشغيل | ‏**عكس التبعية** |

### طريقة النشر

| ‏الحالة | ‏الطريقة |
|---|---|
| ‏الطريقة الوحيدة التي يهيئها هذا المستودع | ‏**IIS على ويندوز، باستضافة داخل العملية تحت `AspNetCoreModuleV2`** |

**ولا توجد في هذا المستودع صورة حاوية، ولا ملف تنسيق حاويات، ولا بيان تنسيق تشغيل، ولا ملف تعريف نشر إلى سحابة مُدارة.** 
وانتبه لملف `web.config`، فنصفا المنتج يعاملانه معاملتين مختلفتين. فملف `web.config` الخاص بأيٍّ من تطبيقَي .NET ليس في git — بل يُنتجه الأمر `dotnet publish` ثم يُحرَّر على الخادم لضبط نموذج استضافة IIS على `inprocess` واسم البيئة على `Production`، وهو متجاهَل عمداً لأن النسخة المنشورة منه تحمل أسراراً. أما تطبيقا الواجهة أحاديّا الصفحة فالعكس تماماً: فملفا `web.config` الخاصان بهما **متتبَّعان** في git تحت المسار `apps/<app>/public/`، والبناء ينسخ كلاً منهما إلى مجلد إخراج تطبيقه.

**ولا يوجد تكامل مستمر ولا تسليم مستمر.** فمجلد سير العمل موجود وفارغ. والنشر يجري بأمر «Publish» من Visual Studio لتطبيقَي .NET، وبنشرٍ يدوي لقاعدة البيانات، وبنسخِ ملفات يدوي لتطبيقَي الواجهة.

### ما هو داخل التحكم بالمصدر وما هو خارجه

وهذا أهم مما يبدو، لأن المشغّل الذي يفترض أن «الإعدادات موجودة في git» يفقد كل ما يلي.

| ‏متتبَّع؟ | ‏الملف |
|---|---|
| ‏**نعم** | ‏`Auth_API/appsettings.json` و`appsettings.Development.json` |
| ‏**نعم** | ‏`API_Gateway/appsettings.json` و`appsettings.Development.json` |
| ‏**نعم** | ‏ملفا `public/web.config` و`.env.production` في كلا التطبيقين |
| ‏**لا** — مُستبعَد | ‏`appsettings.Production.json` (في أي من العمليتين) |
| ‏**لا** — مُستبعَد | ‏`web.config` (في أي من عمليتَي .NET) |
| ‏**لا** — مُستبعَد | ‏`appsettings.*.local.json` |
| ‏**لا** — مُستبعَد | ‏ملفات تعريف النشر (`*.pubxml`) وملفات تعريف نشر قاعدة البيانات |

**والنسخة النظيفة من المستودع لا تحوي أي إعداد إنتاجي على الإطلاق.** والملفات المستبعَدة مستبعَدة لأنها تحمل أسراراً: فملف `Auth_API/web.config` في شجرة منشورة يحمل نص اتصال قاعدة البيانات بكلمة مروره، وكلمة مرور SMTP، وكلمة مرور شهادة حماية البيانات، بصيغة قيم حرفية لمتغيرات بيئة. فاحتفظ بنسخة احتياطية منها خارج المسار المعتاد، ومشفَّرة.

### التوسع الأفقي

يمكن تشغيل واجهة API نسخاً متعددة خلف موزّع حِمل، لكن **ثلاث قطع من الحالة تخص كل عملية على حدة، ويجب معالجتها صراحةً.** وهذه شروط مسبقة لا تحسينات اختيارية.

1. **حلقة مفاتيح حماية البيانات يجب أن تكون مجلداً مشتركاً.** فالمفتاح `DataProtection:KeyPath` يجب أن يوجّه كل نسخة — من واجهة API ومن البوابة — إلى المجلد نفسه. والنسخ التي لا تتشارك المجلد لا تستطيع قراءة القيم المحمية لدى بعضها، ومنها ملف الأسرار المشفَّر وكل مفتاح تشفير خاص بمستخدم.
2. **إلغاء الرموز لا ينتشر بين النسخ.** فالقائمة السوداء داخل العملية، ولا تُعاد تعبئتها من قاعدة البيانات إلا عند بدء التشغيل. وتسجيلُ خروجٍ تعالجه النسخة «أ» يبقى غير مرئي للنسخة «ب» حتى يُعاد تشغيل النسخة «ب». فخطّط لذلك، أو أنهِ الجلسات عند الحافة.
3. **حدود المعدل لكل نسخة على حدة.** فكلا المحدِّدين نافذة ثابتة داخل العملية، ومن ثَمّ فإن عدد النسخ يضاعف كل حد مضبوط بعدده. فاقسم الأرقام المضبوطة على عدد النسخ، أو افرض الحدود عند حافة مشتركة.

ويظل انعدام الحالة بالمعنى المعتاد صحيحاً: فأي نسخة تستطيع التحقق من أي رمز وصول، لأن التحقق لا يحتاج إلا إلى المفتاح العام.

### نشر قاعدة البيانات

الإجراء يدوي، وكل خطوة فيه مذكورة هنا حتى لا يختبئ شيء خلف كلمة «انشر». نفّذ ما يلي من جذر المستودع ما لم يُذكر غير ذلك.

1. **ابنِ مشروع قاعدة البيانات.** افتح `Auth/Auth_DB/Auth_DB.sqlproj` في Visual Studio وابنِه، أو ابنِه بأدوات SSDT. والنجاح يبدو هكذا: ظهور ملف `.dacpac` في مجلد مخرجات المشروع.
2. **انشر ملف DACPAC** على قاعدة البيانات الهدف، من نافذة Publish في Visual Studio أو بأداة سطر الأوامر `SqlPackage`. والنجاح يبدو هكذا: تقرير نشر مكتمل يسمّي الكائنات التي أُنشئت أو عُدِّلت.
3. **ثم يعمل سكربت ما بعد النشر تلقائياً**، فينفّذ 5 سكربتات ترقية و10 سكربتات بذور عبر التضمين. ولا تشغّل هذه بنفسك.

وثلاثة أمور ينبغي معرفتها قبل الاعتماد على هذا:

- **لا شيء يشغّله نيابةً عنك.** لا خط أنابيب، ولا مشغّل ترحيلات، ولا فحص للمخطط عند بدء التشغيل.
- **لا توجد سكربتات تراجع.** والتعافي من نشرة سيئة يكون باستعادة قاعدة البيانات من نسخة احتياطية.
- **توجد أربعة ملفات تعريف نشر، وليس منها واحد في git**، فالهدف المعتمد لكل بيئة غير مسجَّل في هذا المستودع.

## 12. المراقبة والرصد

### التسجيل المنظم (Serilog)

كلتا العمليتين تستعملان Serilog. وهو يلتقط خصائص السجل بصورة منظمة في داخله، وهذا ما يجعل السجلات قابلة للاستعلام متى وُصِل بها مَخرَج (sink) يفهم تلك البنية.

**وكلتا العمليتين تكتبان نصاً عادياً لا JSON.** فكل مَخرَج يستعمل قالب إخراج نصياً، ولا يُسجَّل أي مُنسِّق JSON، ولا يشير أيٌّ من المشروعين إلى حزمة تنسيق JSON. ويمكن إحلال مَخرَج يُصدِر JSON محلّ المَخرَج الحالي، لكن لا شيء في هذا المستودع يفعل ذلك.

| ‏بوابة API | ‏واجهة Auth API | ‏الإعداد |
|---|---|---|
| ‏نص عادي عبر قالب إخراج | ‏نص عادي عبر قالب إخراج | ‏**تنسيق المخرجات** |
| ‏الطرفية (Console) وملف متدرّج | ‏الطرفية (Console) وملف متدرّج | ‏**المخارج** |
| ‏يومياً | ‏يومياً | ‏**فترة التدوير** |
| ‏`retainedFileCountLimit: 30` — آخر **30 ملفاً** | ‏`retainedFileCountLimit: 30` — آخر **30 ملفاً** | ‏**الاحتفاظ** |
| ‏`FromLogContext` و`WithMachineName` و`WithThreadId` | ‏`FromLogContext` و`WithMachineName` و`WithThreadId` | ‏**الإثراء** |
| ‏`logs/gateway-.log` | ‏`Logs/auth-api-.log` | ‏**مسار السجل المضبوط** |

ويُلحق Serilog التاريخ بجذع الاسم، فتظهر الملفات على القرص بأسماء مثل `auth-api-20260815.log`.

**وكلا المسارين نسبي.** والأساس الذي يُحسب منه هو جذر محتوى العملية، وهو تحت استضافة IIS داخل العملية مجلدُ التطبيق المنشور. وهذا المستودع لا يستطيع ذكر مسار فعلي على الخادم؛ ولمعرفته انظر إلى المسار الفعلي للتطبيق في IIS ثم أضف إليه اسم المجلد المضبوط.

ولا يقبل التعديل من الكونسول — بأثر فوري — إلا مفاتيح الحد الأدنى للمستوى الأربعة في Serilog. أما المخارج والمُثرِيات فتُبنى مرة واحدة عند بدء التشغيل.

### فحوصات الصحة

**توجد أربع نقاط نهاية للصحة موزعة على العمليتين، وفحص قاعدة البيانات ليس على `/health`.**

| ‏الحالة عند الفشل | ‏ما الذي يُفحص | ‏المسار | ‏المضيف |
|---|---|---|---|
| ‏— (صحيح دائماً) | ‏`self` — العملية تعمل | ‏`/health` | ‏واجهة Auth API |
| ‏`Degraded` أو **`Unhealthy`** | ‏`database` (‏SQL Server، بمهلة 5 ثوانٍ) و`signing-key` | ‏`/ready` | ‏واجهة Auth API |
| ‏— | ‏`self` — العملية تعمل | ‏`/health` | ‏بوابة API |
| ‏`Unhealthy` | ‏`auth-api` — مسبار HTTP على مسار `/ready` في واجهة API | ‏`/ready` | ‏بوابة API |

استعمل `/health` لمسبار الحياة في موزّع الحِمل، و`/ready` لمسبار الجاهزية. وجسم الاستجابة له الشكل نفسه على المضيفَين:

ولا يظهر الحقل `error` إلا حين تكون تفاصيل الأخطاء مفعَّلة — أي في بيئة التطوير، أو حين يُضبط `HealthChecks:ExposeErrorDetails` على `true`. وهذا المفتاح يُقرأ مع كل طلب، فيمكن تبديله أثناء التشغيل.

**والنقاط الأربع جميعها لا تُبلَغ إلا بمخاطبة عمليتها مباشرةً.** فهي معفاة من التحقق من رمز البوابة، لكنها ليست ضمن قائمة المسارات المسموح بها في البوابة.

### معرفات الارتباط

**البوابة تَسِم كل طلب تمرّره برأس `X-Correlation-ID`** — ولاحظ أن `ID` بحرفين كبيرين — فتعيد استعمال قيمة المتصل إن قدّمها، وإلا سكّت معرّفاً عالمياً فريداً (GUID) جديداً. وتُدرِج تلك القيمة في سطر سجل الطلب الخاص بها.

**وواجهة Auth API لا تُلحق هذا المعرّف بشيء.** فليست فيها وسيطة ارتباط، ولا مُثرٍ لـSerilog يحمله. والموضع الوحيد الذي تستعمل فيه الواجهة القيمة هو وقوع استثناء غير مُعالَج: إذ تُردّها في جسم استجابة الخطأ. وهي لا تصل إلى أسطر سجل الواجهة نفسها، و`AuditLogs.CorrelationId` **ليس عموداً أصلاً** — فالمستودع يضع فيه القيمة null ثابتةً.

**ومن ثَمّ فالتتبع من طرف إلى طرف عبر العمليتين غير موصول اليوم.** فعامِله على أنه ثغرة، لا ميزة.

### مراقبة أداء التطبيقات

خصائص Serilog المنظمة متوافقة مع الوجهات المعتادة لمراقبة أداء التطبيقات (‏APM — Application Performance Monitoring)، متى أُضيف إليها مَخرَج مناسب:

- **Application Insights** (Azure)
- **Elastic Stack** (ELK)
- **Seq** (خادم سجلات منظمة)
- **Grafana + Loki** (مفتوح المصدر)

ولا شيء من هذه مضبوط في هذا المستودع.

### حزمة SDK كما هي بلا تجميل

يبني مشروع `Auth.Sdk` حزمة باسم `AuthSystem.Sdk` إصدار 1.0.0، تمنح تطبيق .NET من طرف ثالث ثلاثة مخططات مصادقة وسمة صلاحيات. وهي داخل الحل، و**لا يشير إليها أي مشروع**؛ فلا بيان حزمة، ولا هدف تعبئة، ولا أي إعداد للنشر.

وتحمل كذلك عيباً يجدر معرفته قبل تبنّيها: **إذ تضيف الرأس `X-Gateway-Token` مرتين** — مرة عند تسجيل عميل HTTP المسمّى، ومرة أخرى على العميل بعد حلّه. والرأس ذو القيمتين لا يمكن أن يطابق المقارنة أحادية القيمة في الوسيطة، ولذلك يُرفض كل نداء من الحزمة يمر عبر بوابة تتحقق من الرمز بالرمز **403**. وبمعزل عن ذلك، لا تُرفق الحزمة سوى رمز البوابة ولا ترفق رأس `Authorization` قط، بينما تشترط نقطتا `validate` الخاصتان بمفتاح API وبمفتاح Webhook متصلاً مُصادَقاً يحمل صلاحية.

### خارطة طريق التكامل المستقبلي

**وهذه غير مبنية.** ولا يوجد في المستودع اليوم شيء مما يلي.

| ‏الأولوية | ‏الوصف | ‏التكامل |
|---|---|---|
| ‏عالية | ‏مزامنة المستخدمين من أدلة الشركات | ‏**LDAP / Active Directory** |
| ‏متوسطة | ‏اتحاد الدخول الموحّد للمؤسسات | ‏**SAML 2.0** |
| ‏متوسطة | ‏دفع الأحداث إلى أنظمة خارجية | ‏**إشعارات Webhook الصادرة** |
| ‏متوسطة | ‏التكامل مع مزود هوية خارجي | ‏**Azure AD / Entra ID** |

وفي شأن الأحداث الصادرة تحديداً: يوجد تجريد لأحداث التكامل، لكن تنفيذه الوحيد لا يفعل شيئاً. **فلا يغادر العمليةَ شيء.** راجع القسم 19.

### مفاتيح API ومفاتيح Webhook

كلا النوعين قيمة عشوائية طويلة تحمل بادئة موسومة بالبيئة، ويُنشأ ويُلغى من الكونسول، وكلاهما قابل للإلغاء في أي وقت. **لكنهما يُجزَّآن بطريقتين مختلفتين، والفرق مقصود.**

| ‏مفتاح Webhook | ‏مفتاح API | ‏ |
|---|---|---|
| ‏`wk_prod_` و`wk_stag_` و`wk_dev_` و`wk_` | ‏`ak_prod_` و`ak_stag_` و`ak_dev_` و`ak_` | ‏البادئات |
| ‏**HMAC-SHA256** حتمية | ‏**Argon2id** — المعاملة نفسها التي تلقاها كلمة المرور | ‏التجزئة |
| ‏التجزئة الحتمية تتيح البحث بالقيمة في استعلام واحد | ‏التحقق يجرّب المرشحين المجلوبين بالبادئة، فتحمُّل تجزئة بطيئة ممكن | ‏لماذا |
| ‏**لا شيء** — لا وجود لمفهوم النطاقات في مفاتيح Webhook | ‏نعم — كل مفتاح يرتبط بمجموعة صلاحيات | ‏النطاقات |
| ‏`TargetUrl` | ‏— | ‏حقل إضافي |
| ‏معامل الاستعلام `?whk=` | ‏رأس `X-Api-Key` | ‏النقل |

**وتغطية التدقيق جزئية، والفجوة تستحق التصريح.** فإنشاء مفتاح API وإلغاؤه يكتب كلٌّ منهما مدخلاً في سجل التدقيق. أما **استعماله** فلا يكتب شيئاً — إذ يحدّث التحقق طابع آخر استعمال للمفتاح ولا يكتب صف تدقيق. وإنشاء مفتاح **Webhook** أو إلغاؤه لا يكتب مدخل تدقيق البتة، لأن حدثيه بلا معالج.

**وحدود المعدل لكل مفتاح مخزَّنة ولا يُفرض شيء منها.** راجع القسم 19.

## 15. إدارة الأسرار وتدوير المفاتيح

هذا القسم هو الموطن الوحيد لأوضاع التخزين ومادة المفاتيح والتزويد والتدوير. ولا يُوصف شيء يخص المفاتيح في أي موضع آخر من هذا المستند.

### أوضاع التخزين الثلاثة

**توجد ثلاثة أوضاع لا رابع لها**، يختارها المفتاح `SecretManagement:StorageMode`:

| ‏متى تستعمله | ‏أين تعيش الأسرار | ‏الوضع |
|---|---|---|
| ‏بيئة التطوير؛ وهو الخيار الوحيد على مضيف لا يعمل بويندوز | ‏داخل ملف الإعدادات الذي يسمّيه المفتاح `SecretManagement:PlainTextTargetFile` | ‏**`PlainText`** |
| ‏الاستضافة المشتركة، وكل خادم قد تضطر إلى الترحيل عنه — فالشهادة ترافقك | ‏مشفَّرة داخل `secrets.dpapi`، تحميها شهادة X.509 تملكها أنت | ‏**`Certificate`** |
| ‏خادم ويندوز واحد ثابت | ‏مشفَّرة بواجهة حماية البيانات في ويندوز، وهي تربط النص المشفَّر بالجهاز أو بالحساب | ‏**`Dpapi`** |

وDPAPI هي واجهة حماية البيانات المدمجة في ويندوز (Data Protection API): تشفّر البيانات بحيث لا يستطيع فكّها إلا الجهاز نفسه أو حساب المستخدم نفسه.

**والقيم الافتراضية المشحونة تختلف من ملف إلى آخر، وهذا الاختلاف يوقع الناس.** فالقيمة الافتراضية في صنف الإعدادات هي `PlainText`. وملف `appsettings.json` الأساسي يضبط **`Certificate`** للعمليتين كلتيهما. وملف بيئة التطوير يضبط **`PlainText`** صراحةً، مع تعليق يسمّي ذلك العقدَ الفعلي لبيئة التطوير.

**وفي وضع Certificate، غياب الشهادة قاتل خارج بيئة التطوير.** فالعملية ترفض بدء التشغيل. أما داخل بيئة التطوير فترتد إلى `PlainText` مع تحذير.

### أين تعيش مادة المفاتيح

| ‏القيمة الافتراضية عند ترك المفتاح فارغاً | ‏مفتاح الإعداد | ‏العنصر |
|---|---|---|
| ‏`%LOCALAPPDATA%\AuthSystem\Secrets\secrets.dpapi` | ‏`SecretManagement:SecretFilePath` | ‏ملف الأسرار المشفَّر |
| ‏`%ProgramData%\AuthSystem\Keys` | ‏`DataProtection:KeyPath` | ‏حلقة مفاتيح حماية البيانات |
| ‏لا شيء — ووضع Certificate يفشل بدونها | ‏`DataProtection:Certificate:PfxPath`، أو `:Thumbprint` للتحميل من مخزن ويندوز | ‏الشهادة الحامية |
| ‏— | ‏متغير البيئة الذي يسمّيه `DataProtection:Certificate:PasswordEnvironmentVariable`، وافتراضه `AUTH_DP_CERT_PASSWORD` | ‏كلمة مرور الشهادة |
| ‏`[]` | ‏`DataProtection:Certificate:AdditionalPfxPaths` — يُحتفظ بها لتبقى مدخلات حلقة المفاتيح القديمة مقروءة بعد التدوير | ‏الشهادات المُستبدَلة |

**ووجّه واجهة API والبوابة إلى مجلد حلقة المفاتيح نفسه.** فكلتاهما تستعمل اسم تطبيق حماية البيانات `AuthSystem`، وكلتاهما يجب أن تقدر على قراءة القيم المحمية نفسها.

### الأسرار التي لا تبدأ العملية بدونها

| ‏قابل للتدوير؟ | ‏مفتاح الإعداد | ‏السر |
|---|---|---|
| ‏قابل للتدوير | ‏`Jwt:PrivateKeyPem` | ‏مفتاح توقيع JWT (مفتاح RSA خاص بصيغة PEM) |
| ‏قابل للتدوير | ‏`Jwt:RefreshTokenHmacKeyPlain` | ‏مفتاح HMAC لرموز التحديث |
| ‏قابل للتدوير | ‏`Gateway:ExpectedToken` | ‏رمز البوابة (جانب واجهة API) |
| ‏**دائم — لا يُدوَّر أبداً** | ‏`AccountDeletion:IdentifierHmacKeyPlain` | ‏مفتاح HMAC لمعرّفات حذف الحسابات |
| ‏قابل للتدوير | ‏`Gateway:Token` | ‏رمز البوابة (جانب البوابة) |

**ومفتاح معرّفات حذف الحسابات دائم.** فكل حجز في سجل الحذف تجزئة محسوبة به. وتدويره يعني أن السجل لن يتعرّف بعد ذلك على معرّف أُتلف، ومعناه العملي أن عنوان بريد محذوفاً يصير قابلاً للتسجيل من جديد قبل انقضاء مدة حجزه. فاحتفظ بنسخة احتياطية منه، ولا تولّده من جديد أبداً.

ويوجد مفتاحان آخران تديرهما طبقة الأسرار لكنهما ليسا شرطاً لبدء التشغيل: `ExternalAuth:Apple:PrivateKeyPem` (مفتاح التوقيع `.p8` الخاص بـApple)، وكلمة مرور SMTP في `Email:Password`.

**ويرفض حارسٌ عند بدء التشغيل إقلاعَ النظام إذا وُجد أي سر من الجواهر في إعدادات الإنتاج بنص صريح.** وهو يفحص `Jwt:PrivateKeyPem` و`Jwt:RefreshTokenHmacKeyPlain` و`AccountDeletion:IdentifierHmacKeyPlain` و`ExternalAuth:Apple:PrivateKeyPem`، ويعمل *قبل* تركيب مزوّد الأسرار في طبقات الإعدادات.

### التزويد

- **المفتاح `SecretManagement:AutoGenerateKeys` قيمته الافتراضية `true`**، والتوليد لا يقع إلا حين لا يكون ملف الأسرار موجوداً. والأحجام المولَّدة: RSA بطول 2048، ومفتاح HMAC ورمز البوابة والفلفل 32 بايتاً لكل منها.
- **اضبطه على `false` بعد أول بدء تشغيل ناجح**، ليفشل السر المفقود فشلاً صريحاً بدل أن يُولَّد من جديد في صمت — فالتوليد الصامت يُبطل كل رمز قائم.
- **وأحضر مفاتيحك الخاصة** باستيرادها عبر نقاط نهاية الإدارة المذكورة أدناه (في وضعَي Certificate وDpapi)، أو بكتابتها في `appsettings.Production.json` (في وضع PlainText). وهذا هو ما يجعل ترحيل الخادم ممكناً دون إخراج كل مستخدم من جلسته. راجع [PRODUCTION_DEPLOYMENT_GUIDE.md §F — Provision your own keys (BYOK)](PRODUCTION_DEPLOYMENT_GUIDE.md#f-provision-your-own-keys-byok--painless-migration) (متاح بالإنجليزية وحدها).

### تأكيد رفع المستوى الذي يحرس العمليات المدمِّرة

**كل عملية توليد أو استيراد تشترط تأكيداً ثانياً من المسؤول نفسه.** وهذا من أقوى ضوابط النظام، ومن أسهلها إغفالاً.

| ‏القيمة | ‏الخاصية |
|---|---|
| ‏6 أرقام، مجزّأة بـArgon2id، تُرسل بالبريد إلى المسؤول الطالب | ‏الرمز |
| ‏`Email:OtpExpirationMinutes` (افتراض الصنف 15 دقيقة، والمشحون 5 دقائق) | ‏نافذة إدخال الرمز |
| ‏**5**، مثبتة في الشيفرة. والمحاولة تُحجَز بتحديث شرطي في قاعدة البيانات *قبل* التحقق من التجزئة، فلا يمكن استغلال بطء التجزئة لشراء محاولات إضافية | ‏الحد الأقصى للمحاولات |
| ‏**5 دقائق**، مثبتة في الشيفرة وغير قابلة للضبط عن قصد | ‏نافذة الموافقة بعد التحقق |
| ‏المسؤول الطالب، والعملية بعينها، وتجزئة SHA-256 للحمولة. وتُفحص الثلاثة جميعاً من جديد عند صرف الموافقة | ‏ما الذي تُقيَّد به الموافقة |
| ‏استعمال واحد، تُستهلك بتحديث شرطي | ‏إعادة الاستعمال |
| ‏المعرّف المجهول، والمالك الخطأ، والرمز الخطأ، والمنتهي، والمستنفد — كلها تعيد *الخطأ نفسه* | ‏رسائل الخطأ |
| ‏3 تحديات لكل 60 ثانية لكل مسؤول | ‏كبح الإصدار |

وكل نقطة نهاية في متحكم الأسرار تحمل كذلك `[RequirePermission("secrets.manage")]`، والمتحكم كله محكوم بالمفتاح `SecretManagement:EnableAdminApi`.

### ما الذي يفعله التدوير فعلاً

**يوجد مفتاح توقيع RSA نشط واحد في كل لحظة.** فلا قائمة مفاتيح، ولا نافذة مفتاح مزدوج، ومجموعة المفاتيح المنشورة تحوي مدخلاً واحداً. والتحقق يثبّت ذلك المفتاح الواحد.

**وتدوير مفتاح RSA يُبطل كل رمز وصول صدر من قبل.** فعلى حامليه التحديث. ولأن رمز الوصول يعيش 15 دقيقة، فنطاق الأثر نافذة مدتها 15 دقيقة، لا سبعة أيام.

**ورموز التحديث لا يمسّها تدوير RSA.** فهي قيم عشوائية مجزّأة بـHMAC-SHA256، لا موقَّعة بمفتاح RSA. وتدوير مفتاح *HMAC* هو العملية التي تُبطلها.

### كيف تُدوّر المفاتيح خطوةً خطوة

كل خطوة مما يلي نداء HTTP إلى واجهة الإدارة. نفّذها على مضيف واجهة API المنشور، بحساب مسؤول يحمل الصلاحية `secrets.manage`، مع ضبط `SecretManagement:EnableAdminApi` على `true`.

1. **اطلب تحدياً.** ‏`POST /api/v1/admin/Secrets/challenges` — وسمِّ فيه العملية التي تنوي تنفيذها. والنجاح يبدو هكذا: معرّف تحدٍّ في الاستجابة، ورمز من 6 أرقام يصل إلى بريد ذلك المسؤول.
2. **تحقّق من التحدي.** ‏`POST /api/v1/admin/Secrets/challenges/{id}/verify` مع الرمز. والنجاح يبدو هكذا: تأكيد بأن التحدي مُعتمَد. **ولديك الآن 5 دقائق.**
3. **نفّذ العملية.** واحدة من `POST .../generate/rsa` أو `.../generate/hmac` أو `.../generate/gateway-token` أو `.../import/rsa` أو `.../import/hmac` أو `.../import/gateway-token`. والنجاح يبدو هكذا: استجابة تؤكد تخزين المادة الجديدة.
4. **تحقّق من النتيجة.** اجلب `GET /.well-known/jwks.json` وأكّد أن المفتاح المنشور قد تغيّر. ثم سجّل الدخول مرة واحدة وأكّد أنك تستلم رمزاً صالحاً.

**ويوجد مخرجان اضطراريان من سطر الأوامر** للحالة التي تعجز فيها واجهة API عن بدء التشغيل. نفّذهما من المجلد `Auth/Auth_API`؛ وكلٌّ منهما يطبع قيمة مشفَّرة ثم يخرج دون تشغيل الخادم:

</div>

```bash
dotnet run -- --generate-rsa-key
```

```bash
dotnet run -- --generate-hmac-key
```

**لا يتكامل النظام مع أي مدير أسرار خارجي، ولا يمكن ضبط واحد.** فالأوضاع الثلاثة أعلاه هي القائمة كاملة. ودمج خزنة خارجية يقتضي كتابة مزوّد إعدادات جديد، ولا وجود لواحد اليوم.

## 16. الاختبارات

### ما الذي يُختبر اليوم

**يوجد مشروع اختبار واحد للواجهة الخلفية، وإعداد اختبار واحد للواجهة الأمامية.** وكلاهما على مستوى الوحدة.

| ‏القيمة | ‏الواجهة الخلفية |
|---|---|
| ‏`Auth/Auth_API.Tests` — مشروع الاختبار الوحيد في الحل | ‏المشروع |
| ‏xunit 2.9.3، مع Moq 4.20.72 وFluentAssertions 8.10.0 | ‏إطار العمل |
| ‏**176** ملف `.cs`، منها **171** ملفاً يحوي حالات اختبار | ‏ملفات المصدر |
| ‏**1,412** سمة `[Fact]` و**68** سمة `[Theory]`، تغذّيها **241** صفاً من `[InlineData]` ومصدران اثنان من `[MemberData]` | ‏سمات الاختبار |

| ‏القيمة | ‏الواجهة الأمامية |
|---|---|
| ‏Vitest مع jsdom ومكتبة Testing Library | ‏مشغّل اختبارات الوحدة |
| ‏**40** | ‏عدد ملفات اختبارات الوحدة |
| ‏**276** استدعاءً لـ`it()` أو `test()` معدودة في المصدر | ‏عدد حالات اختبارات الوحدة |
| ‏Playwright | ‏مشغّل الاختبارات الشاملة |
| ‏**5** | ‏عدد ملفات المواصفات الشاملة |

### ما الذي لا يُختبر

والتصريح بهذا صراحةً أهم من الأعداد نفسها.

- **لا توجد قاعدة بيانات في مشروع اختبار الواجهة الخلفية.** فلا اختبار يفتح اتصالاً بـSQL.
- **ولا يوجد مضيف HTTP للاختبار.** فلا اختبار يشغّل واجهة API ويرسل إليها طلباً.
- **ومن ثَمّ لا توجد اختبارات تكامل** بالمعنى المعتاد. فـSQL المستودعات يُمارَس بتحليل نص شيفرة المستودع وسكربتات مشروع قاعدة البيانات، لا بتنفيذ الاستعلامات.
- **ولا توجد اختبارات حِمل ولا اختبارات أداء.** فليس في المستودع كله أداة اختبار حِمل ولا سكربت لذلك.

### اختبارات حراسة تستحق المعرفة

توجد اختبارات عدة غايتها إفشال البناء عند *صنف* من الانحراف، لا اختبار معالج بعينه. والمهندس الذي يقيّم قابلية الصيانة ينبغي أن يعرف بوجودها:

| ‏ما الذي يثبّته | ‏الحارس |
|---|---|
| ‏كل بادئة متحكم يجب أن يقابلها مسار في البوابة، وإلا عادت الميزة كلها بالرمز 404 | ‏تغطية مسارات البوابة |
| ‏الحد الواحد يعيش في ثلاثة ملفات، ويجب أن تتوافق | ‏تطابق حدود المعدل في البوابة |
| ‏القيمة المحفوظة من الكونسول يجب أن تتجسّد على مفتاح الإعداد الدقيق الخاص بها | ‏تغطية تطبيق إعدادات النظام |
| ‏على مولّدَي الأسرار كليهما تزويد كل سر مطلوب | ‏تغطية الأسرار المطلوبة |
| ‏كل ثقافة تحمل المفاتيح نفسها *وعناصر التنسيق النائبة نفسها* | ‏تطابق أساس الترجمة |
| ‏كل رمز خطأ في المجال له مدخل ترجمة | ‏تغطية موارد أخطاء المجال |
| ‏يحلّل المخطط بحثاً عن المفاتيح الأجنبية، فأي جدول جديد يشير إلى المستخدمين يُفشل البناء ما لم يشمله التطهير | ‏SQL الحذف النهائي للمستخدم |
| ‏كل سكربت بذور مُضمَّن يجب أن ينتهي بفاصل الدفعات الخاص به | ‏تركيب سكربت ما بعد النشر |

### التغطية

**لا تُفرض أي نسبة تغطية في أي موضع، ولا يمكن ذكر واحدة.** فمشروع الاختبار يشير إلى جامع تغطية، لكن لا عتبة، ولا مهمة تقرير، ولا خط أنابيب يفحص مخرجاته. ومجلد سير العمل فارغ. وكل رقم تغطية ورد في وثائق قديمة كان طموحاً لا قياساً.

## 17. مرجع الإعدادات

### من أين يمكن أن تأتي القيمة

إعدادات .NET تعمل بقاعدة «آخر مزوّد يفوز»: فحين يُعرَّف المفتاح نفسه في أكثر من موضع، تسود القيمة الآتية من المزوّد المضاف أخيراً. وهذا النظام يضيف عدة مزوّدين، والترتيب الناتج يهمّ فعلاً حين تظهر القيمة في مكانين. وهذا هو الترتيب، من الأعلى أولويةً إلى الأدنى:

</div>

```text
newly minted pepper material, in memory (only on the boot that mints it)
  > database settings overrides (edited in the admin console)
    > encrypted secrets file (or generated secrets, in PlainText mode)
      > command-line arguments
        > environment variables
          > appsettings.{Environment}.local.json   (git-ignored)
            > appsettings.{Environment}.json
              > appsettings.json
```

<div dir="rtl" lang="ar">

وقيدان اثنان يبقيان هذا الترتيب صادقاً:

- **طبقة قاعدة البيانات لا تمسّ مفاتيح الأسرار إطلاقاً.** فمزوّد التجاوزات يتخطى كل مفتاح موسوم بأنه مملوك للأسرار، وكل حقل لا يعلّمه السجل قابلاً للتعديل، ومسار الكتابة يرفض المفاتيح نفسها. فقول «قاعدة البيانات تغلب الأسرار» صحيح على الورق، لكن مجموعتَي المفاتيح منفصلتان تماماً بحكم البناء.
- **وملف الأسرار يغلب متغيرات البيئة فعلاً**، بما في ذلك نص اتصال مُمرَّر عبر `ConnectionStrings__AuthDb`. ولهذا وُجد مخرج الطوارئ `AUTH_IGNORE_SECRET_CONNECTIONSTRING`.

### متغيرات البيئة التي تقرؤها الشيفرة

| ‏الأثر | ‏المتغير |
|---|---|
| ‏يختار ملفات إعدادات البيئة، ويتحكم في كل فرع مخصص لبيئة التطوير وحدها | ‏`ASPNETCORE_ENVIRONMENT` |
| ‏يزوّد نص اتصال قاعدة البيانات (الشرطتان السفليتان تقابلان `ConnectionStrings:AuthDb`) | ‏`ConnectionStrings__AuthDb` |
| ‏يزوّد كلمة مرور SMTP | ‏`Email__Password` |
| ‏الاسم الافتراضي للمتغير الذي يحمل كلمة مرور شهادة حماية البيانات | ‏`AUTH_DP_CERT_PASSWORD` |

### عقد الاستجابة

**لا يوجد غلاف.** فجسم الاستجابة الناجحة هو كائن نقل البيانات نفسه. ولا يوجد في مسار النجاح أي غلاف من نوع `success`/`data`/`errors` في أي موضع.

- أسماء الخصائص بصيغة **camelCase**.
- **والخصائص الفارغة (null) تُحذف** من الاستجابات كلياً.
- **والقيم المعدودة (enums) تُسلسَل بأسمائها النصية**، لا بأرقامها.
- وقيم `DateTime` تُصدَر دائماً وفي آخرها الحرف `Z`.

ونقاط النهاية التي تعيد قوائم تعيد صنف صفحة خاصاً بكل كيان — فلا يوجد صنف عام `PagedResult<T>` — على هذا الشكل:

</div>

```json
{
  "users": [],
  "totalCount": 0,
  "pageNumber": 1,
  "pageSize": 20,
  "totalPages": 0,
  "hasPreviousPage": false,
  "hasNextPage": false
}
```

<div dir="rtl" lang="ar">

واسم خاصية المجموعة يتبع اسم الكيان، فهي `users` هنا و`logs` في نقطة نهاية سجل التدقيق. **وحجم الصفحة محصور بين 1 و100؛ وأي قيمة أكبر تعيد 400.**

### عقد الأخطاء

أخطاء المعالجات وأخطاء النطاق تعود بصيغة `ProblemDetails`، ومعاني حقولها ليست المعاني المتعارف عليها:

</div>

```json
{
  "status": 404,
  "title": "User.NotFound",
  "detail": "The requested user was not found.",
  "instance": "/api/v1/users/3f2a..."
}
```

<div dir="rtl" lang="ar">

- **الحقل `title` هو رمز الخطأ**، لا عنواناً يقرؤه إنسان. فاكتب برمجتك عليه.
- **والحقل `detail` هو الرسالة البشرية المترجمة**، بحسب لغة الطلب.
- **والحقل `extensions.errors`** لا يظهر **إلا حين يكون هناك أكثر من خطأ واحد**، فيكون مصفوفةً من `{ code, description }`.

وربط رموز الحالة: خطأ تحقق ← 400، وغير موجود ← 404، وتعارض ← 409، وممنوع ← 403، وغير مصرَّح ← 401، وما عدا ذلك ← 500.

وأربع استجابات لا تتبع هذا الشكل عن قصد، وكاتب العميل يحتاج إلى الأربع جميعاً:

| ‏الشكل | ‏الحالة |
|---|---|
| ‏`{ "error": "...", "retryAfter": 60.0 }` — راجع القسم 3 | ‏رفض بسبب حد المعدل (429) |
| ‏`application/problem+json` بالحقول `type` و`title` و`status` و`detail` و`instance` | ‏رفض بسبب رمز البوابة (403) |
| ‏`application/problem+json`، والعنوان `Unauthorized` | ‏رمز مدرج في القائمة السوداء (401) |
| ‏`{ "error": "..." }` — متحكم الصور لا يرث من الصنف الأساس المشترك | ‏فشل رفع صورة |

### مستند OpenAPI

**مستند OpenAPI لا يُقدَّم إلا في بيئة التطوير، على المسار `/openapi/v1.json`.** وهو من إنتاج الدعم الأصلي لـOpenAPI في .NET 10.

**ولا تقدّم واجهة API أي صفحة توثيق تفاعلية في أي بيئة** — فلا يوجد فيها مستكشف API قابل للتصفح من أي نوع. وفي بيئة الإنتاج لا تعرض وصفاً للواجهة إطلاقاً.
