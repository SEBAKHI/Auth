# AuthSystem

## منصة هوية مؤسسية — مصممة للمنظمات متعددة التطبيقات والمستأجرين

---

## الملخص التنفيذي

نظام **AuthSystem** هو منصة شاملة لإدارة الهوية مصممة لاحتياجات المؤسسات الفعلية. تم بناؤه من الصفر لمعالجة قيود أنظمة إدارة الهوية التقليدية — وبالأخص نظام ASP.NET Identity الافتراضي من Microsoft، الذي يقدم حلاً واحداً يناسب الجميع لكنه سرعان ما يقصر في البيئات المعقدة متعددة التطبيقات.

يوفر AuthSystem حلاً **مرناً** و**آمناً** و**قابلاً للتخصيص** بشكل كبير ومصمماً وفقاً للاحتياجات المحددة للمؤسسات النامية.

> **للنظرة السريعة من صفحة واحدة**، راجع [AUTH_SYSTEM_EXECUTIVE_SUMMARY_AR.md](AUTH_SYSTEM_EXECUTIVE_SUMMARY_AR.md)
> **لتفاصيل البنية التقنية**، راجع [AUTH_SYSTEM_TECHNICAL_DEEP_DIVE_AR.md](AUTH_SYSTEM_TECHNICAL_DEEP_DIVE_AR.md)

### تحدي الهوية الذي تواجهه مؤسستك

| AuthSystem | الأنظمة التقليدية | التحدي |
|------------|-------------------|--------|
| يستخدم **Argon2id** المعيار الذهبي الموصى به من OWASP | تستخدم خوارزميات لا تقاوم هجمات GPU الحديثة بنفس الفعالية (bcrypt) | **أمان كلمات المرور** |
| **صلاحيات هرمية** مع أحرف البدل مثل `admin:*` | أدوار مسطحة بمرونة محدودة | **إدارة الصلاحيات** |
| **تطبيقات متعددة** تحت مظلة مصادقة واحدة | تطبيق واحد لكل نظام هوية | **دعم التطبيقات المتعددة** |
| **تسجيل شامل** لكل إجراء للامتثال | محدود (يتطلب تنفيذاً يدوياً) | **سجل التدقيق** |
| **مبني للتخصيص** من اليوم الأول | محدود بدون تعديلات كبيرة | **التخصيص** |

> *خوارزمية Argon2id: خوارزمية تجزئة كلمات مرور تعتمد على الذاكرة، فازت بمسابقة تجزئة كلمات المرور الدولية عام 2015 بتحكيم خبراء تشفير رائدين عالمياً. وهي المعيار الذهبي الحالي لتخزين كلمات المرور بأمان، موصى بها من OWASP — المنظمة الرائدة عالمياً في أمان التطبيقات.*

### تكلفة عدم التحرك

المؤسسات التي تعتمد على أنظمة هوية ضعيفة أو مجزأة تواجه مخاطر مالية وسمعة حقيقية:

| التأثير | المخاطرة |
|---------|----------|
| **4.88 مليون دولار** عالمياً (IBM، 2024) | متوسط تكلفة اختراق البيانات |
| حتى **4% من الإيرادات السنوية العالمية** | غرامات عدم الامتثال لـ GDPR |
| **67%** يفقدون الثقة بالشركة | ثقة العملاء بعد الاختراق |
| **80%** من الاختراقات (Verizon DBIR، 2024) | الاختراقات التي تتضمن بيانات اعتماد مسروقة |
| **6 إلى 12 شهراً** من عمل فريق 3-5 مهندسين | بناء ميزات مماثلة داخلياً |

### الخلاصة

نظام AuthSystem هو **نظام بيئي متكامل لإدارة الهوية** ينمو مع مؤسستك مع الحفاظ على أعلى معايير الأمان. يقدم ميزات على مستوى المؤسسات كان سيستغرق بناؤها من الصفر شهوراً — جاهز للاستخدام اليوم.

## 1. نظرة عامة على النظام

### ما هو AuthSystem؟

نظام AuthSystem هو **منصة مركزية للمصادقة والتفويض** تدير:

- **من هم المستخدمون** — المصادقة (Authentication)
- **ما يمكن للمستخدمين فعله** — التفويض (Authorization)
- **ما فعله المستخدمون** — سجل التدقيق (Audit Logging)

فكر فيه مثل **نظام أمان المباني الذكية**:
- **المصادقة** = بطاقة الهوية التي تثبت أنك تعمل هنا
- **التفويض** = الأبواب التي يمكن لبطاقتك فتحها
- **سجل التدقيق** = كاميرا الأمان التي تسجل من ذهب إلى أين

### الميزات الرئيسية في لمحة

- **أمان كلمات المرور بمعايير رائدة** باستخدام خوارزمية Argon2id (موصى بها من OWASP)
- **مصادقة رموز JWT** مع تشفير RS256 غير متماثل
- **نظام صلاحيات هرمي** مع دعم أحرف البدل
- **تحديد معدل الطلبات** لحماية الخدمة وضمان توفرها
- **دعم التطبيقات المتعددة** مع تسجيل دخول موحد عبر تطبيقاتك
- **إدارة المؤسسات** مع تعدد المستأجرين
- **دعم 7 لغات** بما في ذلك لغات RTL مثل العربية والأردية والفارسية
- **سجل تدقيق شامل** للامتثال (GDPR و SOC 2 و HIPAA و PCI-DSS)
- **لوحة إدارة حديثة** مع Blazor
- **بوابة API** مع وكيل YARP العكسي
- **رؤوس أمان متوافقة مع OWASP**

### مجموعة التقنيات

| الغرض | التقنية | المكون |
|-------|---------|--------|
| منطق المصادقة الأساسي | NET 10.0. | واجهة API الخلفية |
| تخزين البيانات | SQL Server | قاعدة البيانات |
| واجهة الإدارة | Blazor — نمط Server و WebAssembly | واجهة الإدارة |
| الوكيل العكسي وتحديد المعدل | YARP | بوابة API |
| تخزين آمن لكلمات المرور | Argon2id | تجزئة كلمات المرور |
| إنشاء رموز آمنة | JWT RS256 | توقيع الرموز |
| وصول عالي الأداء | Dapper | الوصول لقاعدة البيانات |
| تسجيل منظم | Serilog | التسجيل |

> *وكيل عكسي — YARP أي Yet Another Reverse Proxy: مكتبة من Microsoft لبناء خوادم وكيل عكسي عالية الأداء. تقع بين المستخدمين والخدمات الخلفية، توجه الطلبات، توازن الحمل، وتطبق تحديد المعدل.*
>
> *رموز JWT RS256: رموز JSON Web Tokens موقعة باستخدام خوارزمية RSA مع SHA-256. تشفير RS256 غير متماثل — مفتاح خاص يوقع الرموز ومفتاح عام يتحقق منها — مما يسمح بالتحقق الآمن بدون مشاركة الأسرار.*
>
> *مكتبة Dapper: مكتبة Micro-ORM خفيفة لـ .NET تنفذ استعلامات SQL الخام وتربط النتائج بالكائنات. تقدم أداءً أعلى من أنظمة ORM الكاملة مثل Entity Framework لأنها بأقل أعباء إضافية.*
>
> *مكتبة Serilog: مكتبة تسجيل منظم لـ .NET تكتب السجلات كبيانات قابلة للاستعلام (JSON) بدلاً من نص عادي، مما يسهل البحث وتحليل سلوك التطبيق.*

## 2. البنية الأمنية

### تخزين كلمات المرور: Argon2id

خوارزمية **Argon2id** هي **خوارزمية تجزئة كلمات المرور الوحيدة المعتمدة** في AuthSystem. فازت بمسابقة تجزئة كلمات المرور الدولية عام 2015 بمراجعة خبراء تشفير رائدين عالمياً.

#### لماذا Argon2id؟

| القيد الرئيسي | الحالة | مستوى الأمان | الخوارزمية |
|---------------|--------|--------------|------------|
| قابلة للكسر في ثوانٍ | **لا تُستخدم أبداً** | مكسورة | MD5 |
| سريعة جداً — لا مقاومة للقوة الغاشمة | **غير معتمدة** | غير مصممة لكلمات المرور | SHA-256 |
| معالج فقط — لا تقاوم هجمات GPU بنفس الفعالية | **غير معتمدة** | آمنة لكن تم تجاوزها | bcrypt |
| تفتقر لصلابة الذاكرة؛ أضعف ضد الأجهزة الحديثة | **غير معتمدة** | آمنة لكن تم تجاوزها | PBKDF2 |
| لا هجمات عملية معروفة عند الإعداد الصحيح — تستخدم المعالج والذاكرة معاً | **معتمدة** | المعيار الذهبي الحالي | **Argon2id** |

> *ملاحظة: خوارزميات bcrypt و PBKDF2 لا تزال آمنة لحالات استخدام كثيرة ولا تزال موصى بها من OWASP كبدائل مقبولة. ولكن Argon2id توفر مقاومة أفضل ضد هجمات GPU و ASIC الحديثة بسبب تصميمها المعتمد على الذاكرة.*

#### كيف تعمل — شرح مبسط

```

   [خوارزمية Argon2id]
   الذاكرة: 19 ميجابايت (تجعل الهجوم بالقوة الغاشمة مكلفاً)
   التكرارات: مرتان (موصى بها من OWASP 2024)
   الملح: 16 بايت عشوائي (فريد لكل كلمة مرور)
        |
التجزئة المخزنة: $argon2id$v=19$m=19456,t=2,p=1$[salt]$[hash]
```

**لماذا تهم الذاكرة؟** على عكس الخوارزميات البسيطة التي يمكن تشغيلها ملايين المرات في الثانية على وحدات GPU، يتطلب Argon2id ذاكرة تبلغ 19 ميجابايت لكل محاولة. المهاجم الذي يحاول كسر ملايين كلمات المرور بالتوازي سيحتاج تيرابايتات من الذاكرة، مما يجعل الهجوم غير مجدٍ اقتصادياً.

### دفاع متعمّق: الفلفل (Pepper) وفحص كلمات المرور المخترقة

إلى جانب Argon2id، يمكن تفعيل طبقتين اختياريتين لكل بيئة:

- **الفلفل (Pepper)** — سر من جانب الخادم يُمزج في *كل* تجزئة كلمة مرور ويُخزَّن منفصلاً عن قاعدة البيانات (في مخزن الأسرار، وليس في SQL أبداً). إذا تعرّضت قاعدة البيانات وحدها للاختراق، يتعذّر كسر التجزئات المسروقة دون الفلفل. وتُرقّى التجزئات الحالية تلقائياً عند أول تسجيل دخول لكل مستخدم.
- **فحص كلمات المرور المخترقة** — تُفحص كلمات المرور مقابل مجموعة *Have I Been Pwned* باستخدام k-anonymity (لا يغادر الخادم سوى أول 5 أحرف من تجزئة SHA-1؛ ولا تغادره كلمة المرور أبداً). يمكن رفض كلمات المرور المخترقة (`Enforce`) أو الاكتفاء بتحذير عبر ترويسة (`Warn`).

كلتاهما معطّلتان افتراضياً ولا تضيفان أي اعتماد خارجي حتى تُفعَّل.

### المصادقة المبنية على الرموز

بدلاً من التحقق من بيانات الاعتماد مع كل طلب (مثل إظهار الهوية عند كل باب)، نستخدم **الرموز** — مثل سوار الحفل الذي يثبت أنك دفعت عند المدخل.

#### هيكل رموز JWT

| المدة | يحتوي على | المكون |
|-------|----------|--------|
| **15 دقيقة** | معرف المستخدم، الأدوار، الصلاحيات | **رمز الوصول — Access Token** |
| **7 أيام** | معرف الجلسة | **رمز التحديث — Refresh Token** |

#### لماذا تشفير RS256 غير المتماثل؟

|           متماثل (HS256)                                  |
|  نفس المفتاح للتوقيع والتحقق = خطر أمني                 |
|  إذا احتاج الخادم ب للتحقق، فإنه يحتاج المفتاح السري    |

### تحديد معدل الطلبات

تحديد المعدل يضمن توفر الخدمة عبر إدارة حجم الطلبات لكل عميل:

| الغرض | النافذة الزمنية | الحد | نقطة النهاية |
|-------|----------------|------|--------------|
| يضمن نجاح محاولات الدخول الشرعية فقط | 60 ثانية | 5 طلبات | **تسجيل الدخول** |
| يحافظ على توفر الخدمة لجميع المستخدمين | 60 ثانية | 100 طلب | **API العام** |
| إدارة الحركة على مستوى النظام | 60 ثانية | 1,000 طلب | **البوابة** |

**عند تجاوز الحد**، يستجيب الخادم برمز HTTP 429 (طلبات كثيرة جداً) مع رأس `Retry-After` يخبر العميل متى يمكنه المحاولة مجدداً.

### رؤوس الأمان: امتثال OWASP

كل استجابة من AuthSystem تتضمن رؤوس حماية:

| الحماية ضد | القيمة | الرأس |
|------------|--------|-------|
| اختطاف النقرات — Clickjacking | DENY | X-Frame-Options |
| استنشاق MIME | nosniff | X-Content-Type-Options |
| البرمجة عبر المواقع — XSS | 1; mode=block | X-XSS-Protection |
| حقن البرامج النصية | default-src 'self' | Content-Security-Policy |
| تخفيض البروتوكول | max-age=31536000 | Strict-Transport-Security |

> *اختطاف النقرات — Clickjacking: هجوم يتم فيه إخفاء عنصر في الصفحة لخداع المستخدمين للنقر على شيء مختلف عما يرونه. مثلاً، تعتقد أنك تنقر على "تشغيل الفيديو" لكنك فعلياً تنقر على "تحويل أموال".*
>
> *استنشاق MIME: سلوك في المتصفح يحاول فيه تخمين نوع الملف بدلاً من الوثوق بإعلان الخادم. يستغل المهاجمون هذا لتنفيذ ملفات ضارة متنكرة بشيء آمن.*
>
> *البرمجة عبر المواقع — XSS: نصوص برمجية ضارة تُحقن في مواقع موثوقة يمكنها سرقة جلسات الدخول أو البيانات الشخصية أو إعادة توجيه المستخدمين لمواقع مزيفة.*

### الثغرات المخففة

| كيف يمنعها AuthSystem | الثغرة |
|----------------------|--------|
| استعلامات ذات معلمات عبر Dapper — مدخلات المستخدم لا تُعامل أبداً ككود SQL | **حقن SQL** |
| رؤوس Content Security Policy وترميز المدخلات | **البرمجة عبر المواقع — XSS** |
| ملفات تعريف SameSite ورموز CSRF | **تزوير الطلبات — CSRF** |
| تحديد المعدل (5 محاولات/60 ثانية) وقفل الحساب تلقائياً | **القوة الغاشمة — Brute Force** |
| ملفات تعريف آمنة (علامات HttpOnly و Secure) وتدوير الرموز | **اختطاف الجلسة** |
| بروتوكول HTTPS فقط مع إنفاذ HSTS | **رجل في المنتصف** |

### حماية الحساب

| الإعداد | الحماية |
|---------|---------|
| **5 محاولات** | محاولات الدخول الفاشلة قبل القفل |
| **15 دقيقة** | مدة القفل |

| **TOTP مع رموز احتياطية** | المصادقة الثنائية |

## 3. الأداء والسرعة

يحقق AuthSystem أداءً عالياً من خلال أربعة خيارات تصميم رئيسية:

### 1. مكتبة Dapper: تنفيذ SQL مباشر

على عكس أنظمة ORM الثقيلة التي تولد SQL تلقائياً وقد تنتج استعلامات غير فعالة، تنفذ **Dapper** استعلامات SQL مكتوبة يدوياً ومحسنة مباشرة:

| Dapper (مكتبة Micro-ORM) | ORM كامل (مثل Entity Framework) | الجانب |
|---------------------------|----------------------------------|--------|
| مكتوب يدوياً (محسّن) | يُولد تلقائياً (قد يكون غير فعال) | التحكم في SQL |
| أقل (بدون تتبع) | أعلى (تتبع الكائنات) | استخدام الذاكرة |
| مباشر وشفاف | تجريد عالي المستوى | التعقيد |

> مكاسب الأداء أكثر وضوحاً في أحمال العمل كثيفة القراءة على جداول مفهرسة. الأداء الفعلي يختلف حسب البيئة وتعقيد الاستعلام.

### 2. نمط Async/Await: عمليات غير محجوبة

كل استدعاء لقاعدة البيانات غير متزامن مع دعم **CancellationToken** — الخادم يتعامل مع طلبات متعددة بالتزامن دون انتظار إكمال كل منها بالتتابع.

### 3. تجميع الاتصالات — Connection Pooling

اتصالات قاعدة البيانات يُعاد استخدامها من مجمع بدلاً من إنشائها من جديد لكل طلب، مما يلغي عبء إنشاء الاتصالات.

### 4. التخزين المؤقت في الذاكرة

البيانات المستخدمة بشكل متكرر تُخزن مؤقتاً في الذاكرة لاسترجاعها فوراً:

| استراتيجية التخزين المؤقت | البيانات |
|---------------------------|----------|
| في الذاكرة (يُفحص مع كل طلب) | قائمة الرموز الملغاة — Token Blacklist |
| تذكر لكل طلب | عمليات البحث عن الصلاحيات |
| تحميل عند البدء | الإعدادات |

> *قائمة الرموز الملغاة — Token Blacklist: قائمة بالرموز التي أُلغيت ولم تعد صالحة. عند تسجيل خروج المستخدم أو إلغاء رمز، يُضاف إلى هذه القائمة. كل طلب وارد يُفحص مقابل القائمة قبل منح الوصول.*

## 4. إدارة المستخدمين

### دورة حياة المستخدم

تماماً كما يمر الموظفون بمراحل (التوظيف والإعداد والنشاط والمغادرة)، للمستخدمين دورة حياة مماثلة:

</div>

```
+--------------+    +--------------+    +--------------+
|   تم إنشاؤه  | -> |   نشط       | -> |  غير نشط    |
| (في انتظار  |    | (وصول      |    | (معلق)      |
| التحقق)     |    |  كامل)      |    |              |
+--------------+    +--------------+    +--------------+
       |                  |                  |
       |                  v                  |
       |           +--------------+          |
       |           |   مقفل      |          |
       |           | (محاولات    |          |
       |           |  كثيرة)     |          |
       |           +--------------+          |
       |                                     |
       +-------------------------------------+
                       محذوف
                  (حذف ناعم — Soft Delete)
```

<div dir="rtl" lang="ar">

> *الحذف الناعم — Soft Delete: بدلاً من حذف سجل المستخدم نهائياً، يُعلّم النظام السجل على أنه "محذوف" مع طابع زمني. تبقى البيانات سليمة ويمكن استردادها عند الحاجة — مثل نقل ملف إلى سلة المحذوفات بدلاً من محوه نهائياً.*

### ميزات ملف المستخدم

| الوصف | الميزة |

| المعرف الأساسي (فريد لكل مستخدم) | **البريد الإلكتروني** |

| صورة رمزية قابلة للتخصيص | **صورة الملف الشخصي** |

### مصمم للتوسع

| التأثير | التحسين |
|---------|---------|

## 6. الأدوار والصلاحيات

### نظام الصلاحيات الهرمي

تماماً كما للشركة تسلسل هرمي (الرئيس التنفيذي ثم المدراء ثم المشرفون ثم الموظفون)، للصلاحيات أيضاً تسلسل هرمي.

### تنسيق الصلاحيات

الصلاحيات تتبع **تنسيق كود هرمي**:

</div>

```
resource:action:subaction

أمثلة:
|-- users:read        (قراءة أي مستخدم)
|-- users:create      (إنشاء مستخدمين)
|-- users:update      (تحديث مستخدمين)
|-- users:delete      (حذف مستخدمين)
|-- users:*           (جميع عمليات المستخدمين)
|-- roles:read        (قراءة الأدوار)
|-- roles:permissions (إدارة صلاحيات الأدوار)
+-- *                 (كل شيء - المسؤول الأعلى)
```

<div dir="rtl" lang="ar">

### مطابقة أحرف البدل — Wildcards

| تسمح بالوصول إلى | الصلاحية الممنوحة |
|------------------|-------------------|
| كل شيء | `*` |
| users:read و users:create و users:update و users:delete | `users:*` |
| crm:leads:read و crm:leads:create و crm:leads:update | `crm:leads:*` |

### التحكم في الوصول المبني على الأدوار — RBAC

الأدوار هي مجموعات من الصلاحيات تُعيَّن للمستخدمين. عند تعيين دور "المدير" بصلاحيات `users:read` و `users:create` و `roles:read` و `audit:read` لمستخدم، يرث تلقائياً جميع هذه الصلاحيات.

### الصلاحيات المحددة بالوقت

الصلاحيات يمكن أن يكون لها **تواريخ انتهاء** — مفيدة للمقاولين، والوصول المؤقت، أو الأدوار المبنية على المشاريع.

## 10. لماذا تختار AuthSystem على Microsoft Identity؟

### مقارنة صادقة

نظام ASP.NET Identity مكتبة محافظ عليها جيداً مدعومة بمجتمع كبير وتوثيق رسمي شامل. تتكامل أصلياً مع نظام Microsoft البيئي وهي خيار ممتاز لسيناريوهات المصادقة المباشرة.

لكن عندما تحتاج المؤسسات إلى **تسجيل دخول موحد متعدد التطبيقات**، و**إدارة متعددة المستأجرين**، و**صلاحيات هرمية**، و**سجل تدقيق شامل**، يتطلب ASP.NET Identity تطويراً مخصصاً كبيراً لتحقيق ما يوفره AuthSystem جاهزاً.

| AuthSystem | Microsoft Identity | الجانب |
|------------|-------------------|--------|
| Argon2id (المعيار الذهبي الموصى به من OWASP) | bcrypt (آمنة، لكن Argon2id أفضل ضد GPU) | **خوارزمية كلمة المرور** |
| هرمي مع أحرف البدل | مبني على المطالبات (مسطح) | **نموذج الصلاحيات** |
| تسجيل دخول موحد مدمج عبر جميع التطبيقات | يتطلب إعداداً منفصلاً لكل تطبيق | **التطبيقات المتعددة** |
| دعم أصلي متعدد المستأجرين | غير مشمولة (تتطلب تطويراً مخصصاً) | **المؤسسات** |
| شامل وتلقائي | يتطلب تنفيذاً مخصصاً | **سجل التدقيق** |
| مدمجة عبر YARP | تبعية خارجية | **بوابة API** |
| مدمج | تبعية خارجية | **تحديد المعدل** |
| TOTP كامل مع رموز احتياطية | دعم أساسي | **المصادقة الثنائية** |
| تحكم كامل (جلسات متزامنة، مهلة خمول) | تحكم محدود | **إدارة الجلسات** |
| 7 لغات جاهزة | إعداد يدوي | **واجهة متعددة اللغات** |
| توثيق متنامٍ | مجتمع كبير، توثيق شامل | **المجتمع والتوثيق** |
| عبر بروتوكولات قياسية | تكامل أصلي | **تكامل Azure** |

### متى تختار AuthSystem

AuthSystem هو الخيار الأفضل عندما تحتاج مؤسستك:
1. **تطبيقات متعددة** تشترك في نظام هوية واحد
2. **دعم متعدد المستأجرين/المؤسسات**
3. **صلاحيات هرمية** تتجاوز الأدوار المسطحة
4. **سجل تدقيق جاهز للامتثال** بدون تطوير مخصص
5. **تحكم كامل** بسياسات الأمان وإدارة الجلسات

### متى قد يكفي Microsoft Identity

قد يكون Microsoft Identity كافياً عندما:
1. لديك تطبيق واحد مع وصول بسيط مبني على الأدوار
2. لا تحتاج تعدد المستأجرين أو صلاحيات هرمية
3. تفضل الاعتماد على نظام Microsoft البيئي المدمج
4. متطلبات التدقيق لديك محدودة

### مسار الترحيل

</div>

```
المرحلة 1: نشر AuthSystem بجانب النظام الحالي
المرحلة 2: ترحيل بيانات المستخدم (كلمات المرور يمكن إعادة تجزئتها عند أول تسجيل دخول)
المرحلة 3: تحديث التطبيقات لاستخدام AuthSystem
المرحلة 4: إيقاف نظام الهوية القديم
```

| هوية واحدة عبر جميع تطبيقات الشركة — تقليل الاحتكاك وتكاليف الدعم | **دعم التطبيقات المتعددة** |
| معرفة من فعل ماذا ومتى بالضبط — التحقيق في الحوادث في دقائق | **تدقيق شامل** |
| تجنب 6-10 أشهر من التطوير المخصص لميزات مماثلة | **تقليل تكاليف التطوير** |
| بنية نظيفة وأنماط متسقة تقلل تكاليف الصيانة طويلة المدى | **كود قابل للصيانة** |

### تقييم سريع لنظام الهوية الحالي

إذا أجابت مؤسستك بـ "لا" على ثلاثة أو أكثر من هذه الأسئلة، فقد تستفيد من AuthSystem:

1. هل يستخدم نظامك خوارزمية تجزئة كلمات مرور تعتمد على الذاكرة؟
2. هل يمكنك تدقيق من وصل إلى أي بيانات ومتى؟
3. هل تدعم تسجيل دخول موحد عبر تطبيقات متعددة؟
4. هل يمكنك إدارة الصلاحيات بشكل هرمي (ليس فقط أدوار مسطحة)؟
5. هل نظامك جاهز للامتثال مع GDPR / SOC 2؟
6. هل يمكنك إدارة مؤسسات متعددة من منصة واحدة؟
